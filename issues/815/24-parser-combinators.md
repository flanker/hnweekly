## 文章摘要

这是维也纳开发者 Flo（Florian）在个人博客 T3 Blog 上发表的一篇图文教程，以幻灯片加动画的形式，用 TypeScript 从零手写一个迷你解析器组合子（parser combinator）库，最后用它解析 `ping` 命令的完整输出。副标题是「比正则更好」。

**为什么需要它。** 解析就是把文本这类结构较弱的输入转换成对象这类结构化数据。大家熟悉用正则表达式解析文本，也有人知道驱动编辑器语法高亮的重型解析库 tree-sitter。但正则在复杂任务上会变得一团糟，tree-sitter 又常常大材小用。作者认为解析器组合子正好填补这块中间地带，只是知道它的人不多。

**部分解析器。** 最小的单元是「部分解析器」，类型是 `type Parser<T> = (input: string) => [T, string]`：它自己决定在哪里切断输入，返回解析出的值和剩余的字符串。它可以是任意函数，内部甚至可以用正则。比如 `pInteger` 用 `/^\d+/` 匹配开头的数字，对 "10 20 30" 返回数字 10 和剩余的 " 20 30"；`pHello` 检查前缀 "Hello"；`pIgnoreWhitespace` 吃掉空白。依次调用 `pHello`、`pIgnoreWhitespace`、`pInteger`，每一步把上一步剩下的字符串交给下一步，就能把 "Hello 100" 完全消耗掉，得到 `["Hello", null, 100]`。

**三个核心组合子。** 关键在于可以把这条链本身再包装成一个新的解析器。进一步泛化，就得到 `pSeq`：它接收若干解析器，返回一个依次运行它们、把剩余输入往下传递的新解析器。作者展示了如何用 TypeScript 的映射类型和可变参数元组表达它的类型，让 `pSeq(pHello, pIgnoreWhitespace, pInteger)` 被推断为 `Parser<[string, null, number]>`。因为 `pSeq` 把多个解析器组合成新的解析器，所以叫「解析器组合子」：一个接收函数、返回函数的函数，直到最后用数据调用时才真正开始解析。作者还顺带指出，把字符串拆成多个记号的过程与 `.reduce` 互为对偶：reduce 在函数式里叫 fold（折叠），用累加器把多个东西合成一个；这里做的是 unfold（展开），用中间状态把一个东西拆成多个。元组用起来不方便，于是有了第二个组合子 `pMap`，它接收一个解析器和一个函数，把函数作用在解析结果上，比如把元组转成 `{ greeting, who }` 对象。第三个是 `pRepeat`，反复应用一个解析器直到失败（实现上是捕获异常），相当于正则里的 `*`；例如 `pRepeat(pSeq(pNumber, pSemicolon))` 可以解析 "10;20;30;"。

**实战：解析 ping 输出。** 作者先定义了目标类型 `PingResult`，包含头部（目标 IP、解析后的 IP、ICMP 负载大小、总包大小）、每个 ICMP 包（字节数、来源、序号、TTL、耗时）和统计信息（发送数、接收数、丢包率、总时间及 RTT 最小值、平均值、最大值、均方差）。然后准备几个基础零件：匹配固定文本的 `pString`、整数 `pInteger`、带可选小数部分的 `pDecimal`、空白 `pWhitespace`，以及由四个不超过 255 的字节和三个点组成的 `pIpV4Address`。之后头部、单个数据包、两行统计信息都只是一个 `pSeq` 再接一个 `pMap`；最后用 `pRepeat` 收集所有数据包，再用一个 `pSeq` 和 `pMap` 把各部分组合起来，就得到了完整的 ping 输出解析器。作者反问：这些用正则写出来会是什么样子？

**结论。** 一篇文章里从零造出一个手写的组合子库和一个相当复杂的解析器。作者认为这样写出的解析器比正则更容易保证正确、更好维护：嵌套 `pSeq` 时，等价的正则会变得不可读，组合子写法却依然清爽。至于回溯和前瞻这类更高级的功能，组合子同样能处理，因为归根结底都只是组合在一起的函数。

## HN 评论精华

本帖 254 分、近 90 条评论，基调友好。讨论集中在解析器类型签名该怎么设计、组合子在不同语言里的写法和局限，以及作者别出心裁的幻灯片式页面带来的阅读体验问题。作者 schindlabua 本人也在评论区回复。

**类型签名之争。** mrkeen 认为文章起始的类型 `(input: string) => [T, string]` 不好，因为它暗示总会返回一个 T，而解析器其实可能失败；他也不认同「部分解析器」的说法，组合两个解析器得到的仍然是解析器，就像两个整数相加得到整数而不是「和」。作者回应说在 TypeScript 里解析器总可以抛异常（parsimmon 库也是这么做的），他不想在这些技术细节上展开太多。随后 raddan、rhdunn、pyrale、mrkeen 就失败结果应该放进 T 还是由库本身表达争论了一番：mrkeen 主张返回 `Either<Error, (T, Remainder)>`，因为库内部需要根据成功或失败来分支，比如实现「先试第一个、失败再试第二个」的 or 组合子。codebje 和 justinnk 先后引用了那首经典小诗：「解析器就是一个函数，从字符串，到一串由事物和字符串组成的对子」（justinnk 说它出自 Fritz Ruehr，raddan 查到另一说出自 Graham Hutton 的 Haskell 教材）。codebje 解释，用列表而不是 Either 能支持回溯和多种解析结果，代价是非确定性解析可能因回溯而爆炸，建议配合惰性求值。

**组合子的优点与局限。** raddan 维护着一个供学生使用的 TypeScript 解析器组合子库 parsecco，他喜欢这种风格是因为：把一个解析任务看成一个函数很自然，基本不需要单独分词，而且在教学上能帮学生理解柯里化和偏应用。他也提到追求速度时几乎所有人都会手写解析器。amelius 认为文章应该指出局限：无法处理左递归文法，在有歧义的文法上会大量回溯，性能可能呈指数级恶化。gebt 强调正则的问题不只是「乱」，而是形式上就无法解析递归结构，正则语言解析不了上下文无关文法。contificate 指出一个被低估的特点：组合子常写成续延传递风格，于是可以免费获得增量解析，适合处理 TCP 流这类数据，无需像 C 那样手工维护状态机。sovrin 分享了性能经验：在 Node.js 中切割字符串比只传索引慢很多，但用索引会让函数签名不那么优雅。Panzerschrek 则觉得这一切有些小题大做，解析本来就是可以递归调用子函数的普通函数，他写过很多解析器从没需要「组合子」这个名词。

**拆元组的麻烦。** ArneCode 认为组合子相对于解析器生成器的劣势是要写大量映射和拆元组的代码，他在 Rust 中做了一个名为 marser 的库，增加 capture 和 bind 两个组合子把结果存入「桶」中，从而把文法和结果构造分离。pdpi 用 Rust 的 winnow 库写了一个掷骰子表达式解析器，认为并不需要多少拆包代码；Jaxan、kccqzy、black_knight 说在 Haskell 里借助 applicative 风格和 `<*`、`<$` 这类运算符从没遇到这个问题，thedufer 补充 OCaml 的绑定运算符也能起到类似作用。rspeele 讲了 F# FParsec 中 `.>>.` 嵌套元组的丑陋，以及他写的 FParsec-Pipes 库如何用类似正则捕获组的方式解决，并用它写了一个 SQL 解析器。9dev 建议把数据包里冒号后的部分写成通用的键值对解析器，更能体现组合子的优雅；boomlinde 指出第一个地址其实也可能是主机名，正好可以用来演示「多种结构选其一」的情况。

**其他工具推荐。** BoppreH 推荐 Python 标准库里一个几乎没出现在官方文档中的 `re.Scanner`：为每类记号给一个正则和处理函数，一遍扫描得到记号列表，并保证匹配是连续的，适合「单个正则不够用，又犯不着上完整解析器」的场景；me-vs-cat 补充官方文档里其实有一节「编写分词器」。rixed 说 Claude 正在后台帮他修自己多年前用文学编程风格写的 OCaml 组合子库，它支持流式解析和「错误预算」自动修复语法错误。cat-whisperer 说用 nom 写过几个解析器之后，他甚至对英语的细微之处也产生了兴趣。

**页面设计的争议。** 文章采用一边是动画、一边是分段文字的幻灯片式布局，引来不少意见。marginalia_nu 不明白为何不能放在单页里，回看前面的章节很难，也无法搜索；layer8 指出切换页面不会进入浏览器历史，无法用前进后退。akst 说在 MacBook Air 上正文只占大约三分之一的屏幕空间。MattRix 和 smusamashah 则很喜欢这种形式，smusamashah 说多次见到「解析器组合子」这个词，这次终于真正弄懂了。作者回应说他想做一种介于 YouTube 视频和博客之间、可以小口消化的形式，网站正在改版，会改进布局并找台小屏手机测试；被问到动画是否用某个 AI 工具做的，他说用的是普通的 Opus。codethief 称赞他的色彩系列文章，还指出他类型系统系列最后一篇关于柯里-霍华德同构和选择公理的几处错误，作者表示会修改或删掉那一段，免得传播半对半错的说法。
