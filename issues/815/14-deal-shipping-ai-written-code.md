## 文章摘要

这是一个 Ask HN 帖子，发帖人 rzk 转引了一位 Meta 工程师在 LinkedIn 上的自白，说这段话让他很有共鸣，并向 HN 社区抛出问题：你们是怎么处理的？

那位 Meta 工程师写道，他从业以来从未像现在这样对自己的工作感到不安。如今写代码就像在操作一个黑盒：用 AI 交付代码已经成为新的标准，节奏快到如果要逐行检查，就会"永远做不完"。结果就是，你可能搭建出一个自己并不真正理解的系统。你明白高层的设计，却不清楚每个细节。他怀疑这也许就是新常态，但它违背了软件工程师的所有本能，因为工程师习惯于理解自己正在构建的东西。他现在纠结的是：到底需要理解到什么程度，才能安心地继续往前推进？他也想知道其他工程师是否有同样的感受。

这个问题本身很短，却精准地戳中了 2026 年软件行业的一个核心焦虑：AI 编码工具已经让代码产出速度远远超过人类审阅的速度，"理解"与"交付"之间的鸿沟越来越大。它涉及几个层面的问题：工程上，如何保证看不懂的代码是正确的；组织上，出了事谁来负责；职业上，工程师的角色正在变成什么；以及更哲学的一层，程序员对系统的"理解"究竟是什么、从哪里来。帖子获得了大量关注，评论区给出了从"完全不该这么做"到"早就不在乎了"的各种答案，也贡献了不少具体的实践方法。

## HN 评论精华

本帖 615 分、730 多条评论，tptacek 评价说"这类帖子很棒，答案五花八门"。讨论大致分成三种立场：坚持必须读懂代码的一派、把这看作角色转变的一派，以及介于两者之间、试图用设计、测试和工具来弥补理解缺口的实践派。

**最受认同的做法：自己设计，让 AI 填空。** bitwizeshift 的评论引出了全帖最长的讨论（180 多条回复）。他说自己从不让 LLM 设计代码，而是在 UML 层面先搭好完整的抽象层级和各组件的职责、交互方式，再让 LLM 去实现这些空白。这样他也许不知道每个单元内部如何实现，但清楚每个单元的职责和相互关系。他认为 LLM "写抽象的能力糟透了"，无论加多少提示和技能文件，它总能把活干完，但代码往往难以维护，需求一变就得大规模重构。大量用户表示认同，smashed 说即使是公认编码能力很强的 Opus 5.5 也经常写出糟糕或缺失的抽象，因为它可以每次都打补丁应付新需求。davepeck 分享了另一种做法：和 Claude 共同编辑一个 Python 草稿文件来描述 Rust 系统，在乎的地方写清签名、字段和不变量，不在乎的地方留个省略号让 AI 决定。stickfigure 的流程则是：小任务、先花 10 到 15 分钟像和人类同事一样讨论实现方案，再说"动手吧"，代码由他自己提交，"我从不上线我不理解的东西，它总感觉是'我的'代码"。

**也有不少反对声音。** globular-toast 指出设计总有漏洞，人自己写时会撞上这些漏洞并回头修改设计，但 AI 智能体永远不会说"等等，这感觉不对"，你让它在不合理的位置装管道，它就会在你没要求的地板下铺好管道。openasocket 也发现即使设计很明确，LLM 也会在细节里悄悄违背它。threethirtytwo 则认为这种做法已经过时，AI 的设计能力常常超过人类，限制它只会浪费能力。birdsongs 的回复格外心酸：他自己这样写代码，但同事每周改动几千行，他根本审不过来，只能点批准；他在北欧找工作，有个面试官问他懂不懂"NLP"，他以为是玩笑，对方却说是"自然语言编程"，他因此没拿到下一轮。xvector 则坦言自己是 FAANG 的高薪高级开发，只读变更说明就直接合并，"Opus 5.5 会收拾 Opus 4.6 留下的烂摊子，下一代模型也会收拾现在的"。

**测试是答案吗？** ChrisMarshallNY 的回答只有一个词："测试"。他说用 LLM 之后测试做得比以前多得多。SimianSci 反问：这不就是把省下的编码时间挪到了验证上？onion2k 回应说，验证本来就是一直想做却没时间做的事。但质疑也很多：michaelt 指出大量测试意味着更多代码要审；AstroBen 问看不懂的代码要怎么写测试；g-b-r 警告测试抓不住 LLM 加进去的意外行为，比如偷偷联网；egorfine 调侃测试能保证 `sum(1,1)` 等于 2，却保证不了它不会顺手删掉你的主目录。edwin0 担心 AI 同时写代码和测试，两者互相印证却漏掉同一件事。对此 Bootstrapper909 的团队把两者分开，写代码的智能体从不编写评判它的检查；whysosuresh 用 Stryker 做变异测试，第一次就发现上百处测试偏差；fractallyte 和 koliber 都建议用另一家的模型做对抗式审查。quibono 的做法更另类：让 AI 在代码里故意埋 1 到 3 个 bug，看自己能不能找出来。

**"这和当首席工程师、当经理没区别"。** jedberg 和 solatic 都说，首席工程师本来就不可能审阅所有代码，只掌握高层细节；有了 AI，每个人都能像首席工程师那样工作。koliber 回忆自己从初创公司一号员工成长为管理 50 多人的技术负责人，也是逐步放弃了对每行代码的掌控。但 crabbone 尖锐地指出这是偷换概念："我不理解全部代码"和"没有人理解全部代码"之间有天壤之别，以前公司整体上仍拥有这些理解，分散在不同员工身上，责任也能共担；现在可能根本没有人理解。jacquesm 补充，初级工程师至少理解自己在做什么，并且和结果利益相关。globular-toast 则感慨，带 AI 没有看着新人成长的满足感，"这是一条孤独的路"。

**"就像从汇编到编译器"？** hahn-kev 问这是否类似当年从手写机器码转向编译器。Tadpole9181 认为每一次抽象升级都有人反对，从 C 到 Python 到 React 都是如此。但 netburst、curt15、qayxc 反驳：当年人们抱怨的是编译器生成的代码效率低，而不是看不懂，而且编译过程是确定、可解释的，自然语言却是模糊的。

**理解从哪里来。** iamwil 引用 Peter Naur 1985 年的观点：编程是在脑中构建一套关于系统的"理论"，这种理解大多是默会知识，而以往正是靠亲手写代码建立起来的。AI 拿走了这条主要途径，所以人们才会觉得像被蒙住了眼。他的应对是：用访谈式的方式做设计和规格，只做重要的决定，让智能体生成讲解、测验和模拟，再加上验证器和护栏。i2km 反问：如果靠测验来补回理解，那还不如自己写代码。gavinray 坦言转向 Codex 和 Claude 命令行之后，他已无法问心无愧地说自己理解亲手构建的系统，他认为出路是让代码可以形式化验证。tptacek 则选择做工具：他用 SwiftUI 写了一个基于 tree-sitter 和 SCIP 的 PR 阅读器，替换 GitHub 的界面，专门展示调用链、trait 实现等帮助理解的信息。

**"必须读代码"与"早就不在乎了"。** plastic041 说这些评论"令人毛骨悚然"，大家想尽办法逃避阅读自己要负责的代码，至少公司里得有一个人能解释它，"这不是质量问题，是责任问题"。netburst、willio58、mooreds 持同样立场。p_kuni 则从成本角度反驳：对普通 CRUD 业务，让智能体修一个边界 bug 不到 10 欧元，认真审一个大 PR 要 100 到 1000 欧元。egorfine 讽刺说，读 AI 代码并发现它是一团必须推倒的乱麻，在道德上太痛苦，所以大家加入了"我不再读代码"的教会。ramesh31 的回答最丧："你就不在乎了。其他人大概三个月前就不在乎了。"bpavuk 说自己因为在入职两周后把 Claude Code 称为"一个不错的搜索引擎"而被解雇，现在可能要去开卡车。也有人借题吐槽 Meta 本身，ulfw 说"那可是 Meta，交付垃圾是常规操作"。
