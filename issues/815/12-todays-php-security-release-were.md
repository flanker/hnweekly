## 文章摘要

2026 年 10 月 21 日，PHP 项目发布了一次紧急安全更新，修复两个严重的远程代码执行漏洞，官方要求所有 PHP 用户立即升级到 8.5.12、8.4.27、8.3.36 或 8.2.35。当天 PHP 基金会在博客上发了这篇长文，没有讲怎么升级（技术细节和升级说明放在 php.net 的公告里），讲的是这两个漏洞从发现到修复的经过、过去两年 PHP 安全工作在组织上的变化，以及基金会需要依赖 PHP 的机构提供什么支持。

**修复为何拖了两年。** 故事要从 2024 年说起。那一年，PHP 基金会从德国主权技术署（Sovereign Tech Agency）拿到资金，通过 OSTIF 组织了多年来第一次外部安全审计，由 Quarkslab 执行。一名受基金会资助的核心开发者在修复审计报告里的某个问题时，发现了其中一个漏洞的最初迹象。但当时没有找到具体的攻击路径，其他影响更明确的问题也更紧迫，这件事就被搁置了。安全团队提出过几种修复方案，每种都有代价：要么破坏向后兼容，要么引入新的风险，要么需要大量第三方扩展配合修改，而这类协调几乎不可能完成。PHP 安全团队按共识制决策，迟迟选不出方案，又担心选错的后果；加上熟悉引擎底层的核心开发者人数很少、手上事务繁多，修复工作在几个月里反复停滞又重启。基金会在文中直接承认，这次延误是一次“结构性失败”，原因既在安全团队的决策流程，也在资源不足。安全团队已经开始改流程，允许多数票决策，并鼓励妥协方案。

**安全组织的变化。** 过去几个月里，PHP 安全工作的组织方式变化很大。2026 年 5 月，基金会成立了生态安全团队（Ecosystem Security Team），与 PHP 安全团队一起做分诊、协调和加固。Volker Dusch 以基金会“驻场 AI 安全工程师”的身份工作，明显改善了安全团队和基金会之间的沟通与协作。Alexandre Daubois 7 月加入基金会，协助处理和修复安全报告；Daniel Scherzer 9 月加入，负责加固工作。工具方面，基金会今年早些时候与 Alpha-Omega 合作，用 Anthropic 的 Claude Mythos 扫描过 PHP，之后又引入 OpenAI 的 Daybreak Red 来验证报告和漏洞利用，并搭建了覆盖 PHP 所有支持平台、与 CI 一致的 sanitizer 构建和复现环境。

**外部审计让问题浮出水面。** 基金会让 PHP 加入了 Patch the Planet 计划。安全公司 Calif 于 2026 年 7 月 30 日开始审计 PHP，8 月 11 日，Calif 的研究员 Ryan A 报告了一个无条件远程代码执行漏洞，根源正是 2024 年发现的那个问题。OpenAI 也独立报告了同一根源，Wiz（8 月 24 日）和 OpenAI（9 月 18 日）随后又报告了更多攻击路径；Trail of Bits 近期也在审计 PHP。这些报告让问题的严重程度彻底清楚，从 8 月 11 日起，修复它成了基金会安全团队的头号任务。基金会强调，没有资金支持，就不可能让多人全职投入，最后连周末都在昼夜不停地与各方协调。

AI 辅助研究的兴起也让报告数量猛增。据 Alexandre Daubois 上周的文章，7 月 1 日以来团队发布了 15 个 CVE，另外处理了 100 多份无效、重复或无法复现的报告。AI 帮助验证报告、把同一根源的报告归并，但每个判断和每个补丁都由人来做。

**泄露与被打乱的协调披露。** 协调披露一直进展顺利，直到计划发布日前两天：

- 10 月 20 日（周二）约 15:00 UTC，两个 CVE 编号开始在论坛和社交媒体上流传，附带错误的发布时间和错误的 CVSS 10.0 评分（实际为 9.2），但没有泄露技术细节。
- PHP 项目随即在 19:30 UTC 提前发布预告，并把正式发布从 10 月 22 日 14:00 UTC 提前到 10 月 21 日 14:00 UTC。之所以没有立刻发布，是因为发行版还在打包，立即发布会让许多用户没有简便的升级途径，提前一天被认为是最好的折中。
- 约 20:00 UTC，报告漏洞的安全公司之一 Calif 误发了一段视频，展示其概念验证对多个目标生效，透露了少量额外信息。视频很快被删除，但副本已在社交媒体传开，加速了各种 PoC 的出现。
- 约 23:00 UTC 起，基金会开始向少数关键基础设施提供商提供缓解建议，这些建议可能也泄露了出去。安全团队一直在监控出现的 PoC，但截至正式发布时没有发现可用的利用代码。
- 10 月 21 日 07:41 UTC，比约定时间早六个多小时，Chainguard 单方面打破禁令，发布了包含修复的镜像。和其他发行方一样，Chainguard 提前拿到补丁，本是为了让用户能在披露那一刻立即更新。基金会指出，这让任何攻击者都能在其他 PHP 用户还在等待时研究二进制形式的修复，无视了多方数周的协调工作。

**谨慎乐观，以及需要什么。** 基金会认为，这次发布体现了 PHP 安全工作的进步：8 月问题严重性明确之后，安全团队、基金会和发布经理为所有受支持分支交付了修复，发行版和 LTS 供应商也提前拿到了补丁。基金会正在调整流程，让卡在艰难取舍上的严重漏洞能更早上报到基金会领导层，以便及时推动解决，并把这几周的经验变成可重复的流程。

文章最后呼吁资金支持。PHP 支撑着政府服务、网店、银行、媒体等大量网站，但 PHP 本身的安全工作仍依赖一小群基金会资助的开发者和少量志愿者。工具找 bug 越来越快，防守方和攻击方都一样，报告只会越来越多；但决定如何修复引擎里由来已久的设计问题、权衡兼容性、审查补丁，都需要熟悉整个代码库的资深工程师，而这样的人太少。基金会请三类机构出钱：基于 PHP 开发产品和服务的公司，应按依赖程度赞助；托管商、云平台和发行版；以及服务运行在 PHP 上的政府和公共机构，德国主权技术署资助 2024 年审计就是公共投入的范例，基金会希望这类投入能长期持续。文末致谢了安全团队、发布经理、发行版和 LTS 供应商的打包维护者，Calif、Wiz、OpenAI Codex Security、OSTIF、Quarkslab 的研究和负责任披露，提供工具和部分资金的 Alpha-Omega、OpenAI 和 Anthropic，资助 2024 年审计的主权技术署，以及所有赞助方。

## HN 评论精华

这篇帖子获得 806 分、385 条评论。讨论的绝大部分篇幅都在追究这次协调披露为何失控，焦点集中在 Calif 的视频和 Chainguard 提前发布镜像上；其次是 Docker 镜像和托管商跟进慢、开源基金会的资金与决策问题，以及对 PHP 生态的老争论。dang 列出的相关讨论有五六个，其中 php.net 的安全公告帖就有 631 条评论，可见这次事件在 HN 上的热度。

**泄露的源头之一出来道歉**

**petecooper** 承认，CVE 编号提前在 HN 上流传有他的一份责任：他的联系人告诉他没有禁令，联系人的联系人也这么说，第二天早上才发现那是谎话。他为此道歉，随后补了一句：“好在我至少不是 Chainguard。”**cubefox** 的总结很直接：2024 年的问题没修，发布前又有好几方泄露，这次几乎什么都出了错。

**Calif 的视频：营销冲动压过了披露纪律**

**dannyw** 最惊讶的是 Calif 的做法：看到泄露就以为禁令已经失效，抢着发出带动漫舞蹈画面的营销视频。**xp84** 嘲讽“误发”这个说法：录屏、配素材、加特效、渲染、发推，每一步都不像失误。**RamRodification** 和 **thayne** 认为，“误”应该指误判禁令已破，视频多半早就做好了，错在发早了。**MallocVoidstar** 一度质疑视频是在禁令解除时才发的，**Georgelemental** 和 **nicce** 解释说，视频最早提前约一天发出又删除，之后才在约定时间重新发布。

**yardstick** 认为 Calif 和 Chainguard 都有责任，Calif 更大：急于为发现邀功，比让用户有机会更新系统更重要，哪怕在正式发布后等一周再宣传也比现在合适。**kjs3** 觉得这可能就是未来：抢先披露在某些圈子里意义重大，AI 驱动的渗透测试又让每个研究者担心别人很快会找到同一个漏洞，提前抢发的诱惑只会更强。**sippingabonedry** 说这个行业“满是管不住嘴的孩子”，**yreg** 回应说，可正是这些“孩子”发现了漏洞。

**Chainguard 提前发布：背信，还是对客户负责**

这是全帖争论最激烈的部分。**ernubufiei** 认为这对 Chainguard 是“极其严重的指控”；**blantonl** 表示永远不会和 Chainguard 做生意，并指出协调披露依赖信任，Chainguard 今后不应再提前拿到禁令期补丁。**dannyw** 提议建立新规矩，故意打破禁令的公司要被“禁赛”一年，还认为一家受托提前拿补丁的安全供应商打破禁令，比研究者打破禁令性质更恶劣。**martinjc** 认为 Chainguard 用“免费提供”的名义把这件事当成了巨型广告牌。**kijin** 指出，Chainguard 发布的只是基于自家发行版的镜像，其他人无法用它修补自己的系统，真正受益的反而是拿二进制逆向的攻击者。**b112** 认为，即便要提前，也该先通知所有参与方，例如给一小时准备。

也有人替 Chainguard 辩护。**cobolcomesback** 认为 Chainguard 应该被表扬：泄露是别人造成的，其他各方却在等一个协调好的营销发布。**tflinton** 和 **john_strinlai** 说，按惯例，一旦有人提前泄露或出现在野利用，禁令就该结束。**OrderlyTiamat** 认为禁令当时实际上已不存在，Chainguard 对客户有义务尽快发布。**charcircuit** 更进一步，认为协调披露让普通用户无法保护自己。反方的关键反驳是，PHP 安全团队说发布时并未发现可用的利用代码；**angry_octet** 指出 Chainguard 没有拿出在野利用的证据，正确做法是把证据交给协调方，大家一起决定提前发布。**dannyw** 追问这次协调到底有没有一个统一的沟通渠道和协调人。

关于禁令本身还有一场长争论：**semiquaver** 认为 2026 年禁令已经没有意义，传闻就足以让人独立找到漏洞；**hashstring** 坚决反对，认为禁令比以往更必要，光知道“某处有漏洞”并不能帮人找到它，除非禁令被打破、泄露了线索，而这次正是如此。**fg137** 和 **InsidiousWombat** 都认为，如果打破规则没有后果，这种事还会发生；**kbenson** 则提醒，这类协议本身并无约束力。

**PHP 项目的沟通**

**jopicornell** 认为 PHP 方面在泄露后的沟通可以做得更好：预告里说过若细节公开会提前发布，但泄露和视频出现后官方一直沉默，管理员只能在没有可靠信息源的情况下自行判断。他也强调 PHP 是“错得最少的一方”。**bawolff** 和 **Cthulhu_** 则同情 PHP 团队：一个小团队半夜还要准备发布，不可能逐条回应推特上的猜测，而且过度沟通也可能误导用户。**fooker** 补充，所谓“PHP 安全团队”的成员大多还有本职工作，那边同样有危机要处理。

**Docker 镜像、托管商和发行版跟进慢**

**bowersbros** 抱怨禁令解除两小时后官方 Docker 镜像仍未更新。**lol768** 和 **reddalo** 认为 PHP 基金会应该自己维护镜像，所谓“官方镜像”只是 Docker 认可的，并非 PHP 官方制作。**emilburzo** 解释了开源项目的难处：代码和构建流水线都公开，要在禁令期内私下构建，就得另搭一套私有构建系统，私有仓库的免费构建资源又少，没有充足资金就只能简化，还得维护两套系统。**cobolcomesback** 反驳说，他们有两个月时间准备；**dofm** 回应：他们有钱有人吗？PHP 长期资金不足。**inglor_cz** 认为在 AI 驱动的漏洞竞赛时代，私有 CI/CD 流水线对 PHP 这种量级的项目是必需品。**kyriakos** 和 **berkes** 讨论了责任归属：镜像由 Docker 维护，但 PHP 基金会同样不维护 apt/rpm 包，却和各大发行版做了协调。**dofm** 认为大多数 PHP 用户通过发行版软件包获取 PHP，把精力放在发行版上是对的；**berkes** 则提醒官方 PHP 镜像每月下载量超过 300 万次。

**fguerraz** 认为提前获知补丁是巨大的特权，拿到补丁的机构应在几天内完成准备，不该让禁令拖上数周；**Scaled** 解释，有些机构要给 PHP 5.6 这种上游早已放弃的老版本打补丁，自然耗时，**InsidiousWombat** 回应说这等于把企业的技术债变成了全世界的安全问题。托管商方面，**NSUserDefaults** 和 **Cthulhu_** 对 Hetzner 的 Ubuntu 镜像没有及时同步表示失望，不过 Hetzner 的托管服务器已打补丁；**SOLAR_FIELDS** 说 SiteGround 在补丁发布约一小时后就自动为他升级了，反倒是由 Chainguard 维护的 Wolfi 几小时后还没有补丁，并调侃 WordPress 用户早已习惯处理零日漏洞。**InsidiousWombat** 不满“大玩家”总能提前拿到补丁获得免费的安全保护，普通用户则成了二等公民。

**资金与基金会治理**

**imglorp** 抓住了文中“多年来第一次外部审计、靠主权技术署出钱”这一点：万亿美元公司从开源项目中获利却不充分支持，审计这种基本功还要项目自己四处找钱。**eviks** 认为 2024 年的审计结果被白白浪费，共识制是明显的决策缺陷，而 PHP 安全工作依赖一小群人的结构性问题恐怕很难改变。**barelysapient** 推测，Java、Go、.NET 这类由公司主导的语言有经济压力作为推动力，而基金会的共识机制不足以推动关键结果；**rvba** 质疑基金会管理层为何没人关注审计结果。**bombcar** 认为文中“团队按共识运作，迟迟选不出方案”才是真正的新闻：先发布一个方案，再提供编译选项切换到另一个就行。

**PHP 生态现状**

不少评论又回到“PHP 安全吗”的老话题。**dofm** 认为这不是“用 PHP 写的东西不好”的问题，而是某些 C 语言编程方式的问题，性质更接近 Heartbleed 或 log4j，而不是 WordPress 插件漏洞；他挺喜欢现代 PHP，也不认为放弃 PHP 会自动提升安全性。**pseudosavant** 说自己去年已把东西全部迁离 PHP 和 WordPress，因为 PHP 不太重视向后兼容，安全修复只进入较新版本，等于逼着用户不停升级；**technion** 补充，很多公司的官网由市场部或外包维护，默认就是 WordPress。**berkes** 认为 PHP 实际上只有一个主流运行时，一旦出漏洞就影响几乎所有用户，生态需要更多元的实现；**Cthulhu_** 指出 PHP 其实有不少替代解释器，其他语言同样有一个占绝对主导的核心运行时。**muspimerol** 提醒，全球约 30% 的网站跑在 WordPress 上，迁移绝非易事。另有 **xyst**、**alper** 等人发表了“早该淘汰 PHP”之类的评论，**vbezhenar** 则反驳 PHP 如今是相当可靠的语言。

最后，**dofm**、**nedt**、**arjie** 等多位用户感谢 HN 在这次事件中充当了实时信息中枢，大家在评论区互相通报进展、交流应对办法，**UomoNeroNero** 形容这一天“许多聪明人一起尖叫、一起抱怨、一起努力挺过浪潮”。
