## 文章摘要

iOS 开发者 Alberto Denia 用一个比喻来描述智能体编程（agentic coding）给写代码带来的变化：代码过去是石头，现在是黏土。

**从石头到黏土。** 他把 2025 年 11 月之前称为"编程的中世纪"。那时程序员就像石匠，整天小心翼翼地把代码这块石头凿成成品。石头不容情，即使工具不断进步，改起来依然困难：小修小补还行，大改就意味着拆除、搭脚手架、在墙上钉一份周密的计划。智能体编程把这一切翻转了过来。代码本身的"成分"没变，但修改成本骤然坍塌，使它表现得像一种完全不同的材料。

**像雕塑家一样塑形。** 既然是黏土，就可以先拍上几大团，捏出大致形状看看感觉；不喜欢就局部重塑，甚至整个压扁重来。等整体结构对了，再像雕塑家那样从整体体块到中等特征再到细节逐步精修。这种做法可以分形地用于任何层级：独立开发者可以一天之内把整个新产品的核心草绘出来，看看什么可行；负责一个表现不佳功能的团队，可以花两天往完全不同的方向试一试，看转向是否值得。再多的规划和原型图也比不上亲眼看到实物运行。

**判断力依然重要。** 改动几乎免费，但判断改动是否正确并不免费。如果只是一团团往上堆，整个东西很快就会塌成一摊"烂泥"，快到你来不及靠提示词补救。品味、上下文、护栏、架构，这些是黏土雕塑的骨架和窑。至于什么时候、用多少判断力，大家还在摸索，目前出现了按人类参与程度分布的各种工作流，两端分别是"工匠"和"工厂"。

**工匠之道。** 工匠希望自己留在循环里。快速反馈循环是可塑代码最好的地方，也是很多人对它上瘾的原因：去冲杯咖啡的工夫，你就能想到一个功能，在手机上和智能体规划好方案，回到桌前就可以审阅，再打磨几轮，一个完整的产品、工程、QA 周期就压缩成了一个人和三十分钟。当你自己就是用户时，这个循环尤其令人满足。作者在做一个 Markdown 编辑器，有天看到一个记录开销的文件，心想"要是能自动求和就好了……等等，我来扔点代码试试"，半罐汽水的工夫，"计算块"（能求值简单运算并在页边显示结果）的第一版就已经可用了。这算氛围编程（vibe coding）吗？不一定。只评判面向用户的表面，那是氛围编程；同时也评判代码（至少看它的形状），那就是工程，只是循环变快了。

**工厂之道。** 另一端是把自己从循环中移除。工厂的目标是建立系统，把代码黏土压制成能整齐嵌入更大结构的砖块：由规格说明、生成器和验证器（测试、评估、护栏、审查智能体）组成的流水线循环运转，只在万不得已时才上报给人。它最适合结构良好、有可重复模式充当模具、有明确验证标准的代码库，比如添加第十一个 CRUD 接口，或者啃掉一百个小 bug。判断力在工厂里依然存在，只是移到了上游或被嵌入流水线。作者怀疑，搭建能稳定产出可靠结果的工厂，将成为未来工程工作的主要内容。

**工匠还是工厂？** 两者都由人的判断力掌舵，区别在于何时施加：工匠每一轮都在判断，适合探索想法和打磨需要"手感对"的功能；工厂在搭建流水线时预先判断，循环中尽量少介入。人们可能以为工厂只属于大公司，工匠则是在泰国海滩上折腾自己 App 的独立开发者，但二者可以互补：大型成熟产品也需要工匠精神来解决新问题，独立开发者也会想用工厂处理枯燥重复的部分，实现以前单人无法想象的规模。关键是为问题选对方法，而这正是软件工程一直以来的本质。

## HN 评论精华

本帖 257 分、170 多条评论。讨论分成几股：一部分人认同这个比喻并加以延伸，更多人反驳"代码一直都是可塑的"，还有人围绕 AI 重构到底靠不靠谱争得不可开交。

**作者补充。** 作者 albertodenia 在评论区说，文章是几个月前写的，事情发展太快，随着智能体框架越来越好、需要的外围工具越来越少，"工厂"的概念已经变得模糊，但"想留在循环里还是被自动化出去"的区分依然成立。他还列出几个文中没展开的话题：所有权（人们对代码的依恋变弱，好处是少了自尊之争，坏处是责任感下降）、能适应用户的可塑软件、可以完全用代码实现的 3D 图形和动画等资产，以及协作方式的变化（与其开大量会议把每个细节对齐再动手，不如先凭有根据的猜测做出来，再围绕可运行的版本对齐）。

**模具之喻。** theshrike79 说他得出了几乎一样的比喻：编程的未来更多是制作浇注代码的模具，并判断模具精确到什么程度就"够用"；模具做好后，智能体可以用 Swift、Rust、WebAssembly 各浇一个版本。他现在甚至直接把 Claude 交给客户，教他们描述需求并迭代出一个类似 MVP、更多时候是"可交互的 UI 规格说明"的东西，作为构建真正工具的参照。skydhash 反驳说，不用代码表达，模具充其量是个"没形状的袋子"：从自然语言到编程语言，是从有歧义到零歧义，用 AI 把规格翻译成代码，等于让它随机消解规格里的所有歧义，而很多歧义是没有对错、只取决于上下文的权衡。theshrike79 回应说模具不只是提示词，还包括 TLA+ 规格、linter、圈复杂度检查、各层测试和专门写给智能体的文档；skydhash 认为那比直接写代码工作量还大，模具和工厂之所以划算，是因为要生产成千上万个零件。lelanthran 更直接：为什么要用无法检验的人类语言做模具？直接写一个参考实现不就好了。what 则质问：既然让客户自己氛围编程，那他们付钱给你干什么？theshrike79 说客户做的只是 App 的"感觉"和流程，比如给游戏对白文案写手用的专门工具，真正有意义的代码、CI、测试和基础设施仍由"真正的程序员"负责，就像建筑师请客户先画出梦想的房子。

**"代码一直都是黏土"。** 这是评论区最集中的反驳。jameskilton 说代码本来就该是可塑的，所以才有"代码是负债而不是资产，你产生的数据才是资产"的说法；我们的问题在于总让代码僵化、干裂，AI 解决不了这个问题，他预计会出现连大模型都宁愿推倒重来的 AI 代码。haolez、locknitpicker、jodosha、globular-toast 等人纷纷指出"software"里的"soft"本来就是这个意思。globular-toast 还认为大模型反而不太把代码当黏土，因为它们热衷于从零实现、无视现有架构和约定。nomel 则认为代码只对理解力很强的开发者才是可塑的，而这种人其实很少，部分原因是改几行别人的代码得不到认可，"我新建了一个库"才会。由此引出一长串讨论：dehugger 说理解和维护继承来的项目比做新项目更有价值；skydhash 说真正难的往往不是代码本身，而是搞清楚"为什么"，免得拆掉切斯特顿的篱笆（看似多余、实则有用的设计）；mschuster91 吐槽维护老系统得不到上级奖励，因为文化被"简历驱动开发"主导。theshrike79 回击 jameskilton"一听就没碰过遗留代码"：那种 Java 1.x 时代的系统，懂的人早已离职，代码写法让自动化测试几乎不可能，客户永远不会为重构买单；他还举了一个例子，原作者自己重写了链表，前几个元素居然存的是数据的总和、平均值和中位数。作者回应说，手写时设计良好的代码确实有一定可塑性，但与智能体相比仍僵硬一个数量级，可塑性不仅来自可以改，还来自改得快；而"代码随时能重写"在复杂项目中几乎从未真正发生过。crazygringo 帮作者解释：以前一次大重构要几个月，架构定了就基本被锁死，现在一个六个月的迁移一天就能做出可运行的版本，再花几天 QA。

**AI 重构到底行不行。** 这个问题引发了最激烈的分歧。jayd16 说这是幻想：代码改起来慢不是因为改本身费时，而是要重新做所有测试、重新学习上一次那些艰难得来又没写进规格的教训。AdieuToLogic 认为大幅改动系统取决于理解而非时间，智能体编程不会让负责改造产品的人产生理解。反方经验也不少：TheCapeGreek 说过去半年靠 AI 工具在生产系统中完成了好几次高度小众的大规模重构，这种工作手工要好几个月，管理层根本不会批；SmirkingRevenge 在后台把数千行数据转换迁移到完全不同的数据存储，disgruntledphd2 指出这正是有"标准答案"可对照的典型场景，没有基准时效果就差很多；razemio 说他们一个月内用自建工具替换了大部分 SaaS，1dontknow_ 紧张地劝他千万别在生产中用 AI 重写 Keycloak，razemio 澄清只是写了内部工具，Keycloak 照用。XorNot 说 Opus 5.5 写测试比任何开发者都更周全，这让他相信编程已经结束，还说它能发现奇怪的变通写法、背后的 bug 以及被掩盖的竞态条件；disgruntledphd2 则诚恳地追问具体是什么领域和语言，因为这和他的体验完全不符。spiderice 感慨大家对 AI 的体验差别大到几乎没法讨论，YmFzZTY0ZGFkZHk 说他的体验是"屎上堆屎"，前沿模型连中等规模的重构都离不开手把手指导。ianjbutler 给了一些建议：先用 AI 为 AI 搭建约束和护栏，测试套件至少是代码量的两倍，风格问题要么放手、要么用确定性钩子强制执行，提示词永远不管用；discreteevent 反驳说两倍于代码的测试几乎必然绑定实现细节，会让代码更不像黏土。closeparen 说"工厂"式流水线在定义清晰的局部改动（修 lint、修不稳定测试、库迁移）上成功过，但做非平凡的新功能都搞得一团糟，审查和修正的成本比自己全神贯注地带一到三个 Claude Code 会话还高。

**Lisp 早就是黏土。** so-cal-schemer 和 kazinator 指出这个比喻早被用来形容 Lisp：1978 年的 Scheme 修订报告里有"LISP 是一团泥巴，往里加多少泥巴它看起来还是一团泥巴"的说法，1980 年 Byte 杂志的文章改称"黏土"，FOSDEM 2026 还有一场演讲叫《Lisp 是黏土》。so-cal-schemer 认为 Lisp 本质上是一种逻辑汇编记法，非常适合与大模型配合使用。lioeters 补充说 Clojure 生态里甚至有个文学编程工具就叫 Clay。

**更多比喻与质疑。** teleforce 指出亚伯拉罕诸教都说人由黏土造成，derektank 补充了中国女娲造人的神话（先精心捏出贵族，累了就用绳子甩泥点出平民），MPSimmons 打趣说不知是哪个阶级散布的这个神话。评论区还冒出了一堆替代比喻：乐高（AlanKayWasCorre）、花园（deadbabe）、沙坛城（wyum）、一次性塑料（besterman23：廉价、量大、易塑形、随手可扔，污染环境也没人管），以及 angry_octet 引用的《幻想曲》里魔法师学徒那一幕。hexapus 说，你不会用黏土雕一座桥，关键基础设施是用石头建的，要用黏土也得先烧成砖再搭结构，负责任地使用大模型应当是产出可测试、可依赖的离散"砖块"。pinevale 提醒，过去几个月 HN 上大量氛围编程出来的游戏和 GitHub 项目一半跑不起来，如今已被半残地遗弃，因为作者毫无依恋；软件会变多，但好软件或能赚钱的软件是否会变多仍是个问题。作者回应说希望这只是一个阶段，等大家适应了新常态，一天做出来的半残 demo 就会像你昨晚做的饭一样不再引人注目。prmph 针对作者的计算块例子警告：再加几个这样的功能，你就得到一团没有形状、什么都干的软件，AI 不会叫你停下。benoq 则认为代码从来就不是瓶颈，你最终仍要接受市场检验；lez 说"新材料在我们手中"并不对，它在少数几家公司手里，我们是一再恳求的一方。
