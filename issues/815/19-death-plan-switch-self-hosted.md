## 文章摘要

Death Plan Switch 是澳大利亚新南威尔士州乡下一位独立 Web 开发者 Peter Bishop 做的小工具，本质上是一个可以自己部署的「死人开关」（dead man's switch）：它每周给你发一封邮件确认你还好，如果你连续不回应，它会先去问你的直系亲属，最后再通知那些需要接手工作的人。项目免费、MIT 协议，用 PHP 8.1+ 写成，不需要数据库。

**为什么做这个。** 作者在 HN 帖子里讲了背景：他做图形和 Web 技术二十五年，2012 年住院时生意没了，因为没法及时把数据交给他的技术副手，客户很不满。如今他一个人经营 Web 工作室，客户的网站、域名、主机都经他手，如果他突然去世，没人知道东西在哪，甚至没人知道该去找。于是他写了一份应急计划：业务所需的一切都放在一份加密文档里，备份开发者持有密码，律师持有另一份副本。缺的是中间那一环：一个能察觉他「沉默了」、并按正确顺序通知正确的人、又不会因为一个长周末就把家人吓坏的东西。找不到能自己托管的简单方案，他就自己做了一个。

**时间线设计。** 所有步骤都从每周的签到邮件开始计时：第 0 小时发签到邮件，需要你点一个按钮；第 24 小时向你的两个邮箱发提醒；第 48 小时最后一次提醒；第 72 小时询问直系亲属「一切都好吗？」；第 120 小时再提醒亲属；第 144 小时通知各位联系人，每人收到你事先写好的那段话。分支有三种：亲属回复你没事，流程就此结束，其他人什么都不会知道；亲属说出事了，其他联系人立刻收到消息；你在任何阶段签到（哪怕已经触发），所有已被联系的人都会收到「误报」通知。由于邮件每周固定时间发出，联系人最迟会在你最后一次签到后 13 天得到通知。一个细节：仅仅打开链接不算签到，因为邮件安全扫描器会自动打开链接，必须真正按下按钮。

**它不是什么。** 官网列得很清楚：它不是保证，只是发邮件，无法知道你为什么不签到，服务器、定时任务或邮件服务挂了它也就失效；它不是保险箱，不存任何文档和密码，消息里只写东西在哪、该找谁；它不是托管服务，没有账号，你自己跑给自己用；只支持邮件，没有短信、电话或 App；不提供任何担保。

**部署要求。** 需要 PHP 8.1+ 的 Web 服务器（Apache 开箱即用，nginx 要加四行配置）、一个 SMTP 账号、cron 或任何能每 15 分钟请求一次某个 URL 的外部调度器、HTTPS，并且最好托管在与它所保护的网站不同的主机上，避免一次故障同时打掉两边。安装在浏览器里几分钟完成，唯一的技术步骤是 crontab 那一行，安装程序会替你生成。作者说这是他在写了一份详尽的 Markdown 需求文档后借助 Claude Code 写成的，通过了 42 个单元测试；他自己用了几周，客户们觉得这是个很有说服力的卖点。

## HN 评论精华

本帖 108 分、60 多条评论，作者 romeo19361 几乎逐条回复。讨论一半围绕产品设计（签到频率、被动检测、托管风险），另一半是对「AI 写的落地页」「42 个单元测试」以及项目是否太简单的质疑。

**签到频率与流程。** N_Lens 担心自己会忘了回邮件，结果所有人都慌了。作者解释每周一上午 9 点发一封，错过后还会再提醒两次才联系亲属，只有亲属确认出事或不回应时才通知律师和副手。AndrewKemendo 建议改成每月或每季度，并指出 Google 早就有类似的「闲置账号管理器」；作者说选每周是因为即便这样，通知律师和副手也可能要 13 天，而且这不是只管 Google 账号，而是要保证服务器、域名、Dropbox 等业务连续性。iugtmkbdfil834、kevinlanducci、justauserid 都希望间隔可配置，justauserid 甚至想要两三个月；作者表示 V1 固定每周是为了与按月付的账单同步，新版本会考虑放宽。mortmeter 算了个基础概率：45 岁的人某一周去世的几率约为 1/16000，所以几乎每次漏签都会是度假或邮箱满了；作者回应可以暂停最多 28 天。mrheosuper 分享了自己的构想：用 Telegram 或 Facebook 聊天机器人，用自然语言设置消息、收件人和时间，并支持多级消息，先发「某某有事要找你，请尽快联系」，避免一次忘签就把私密遗言发出去。

**被动检测还是主动按按钮。** nirui 说自托管意味着余生都要回邮件告诉程序自己还活着，维护成本不低，还得保证服务器一直通电联网，「不知道是生命先结束还是我先烦了」；他建议改成被动保活，比如设备解锁使用时自动发心跳。作者认为自动保活在你死后也会继续发信号；nirui 反驳这只是信号采集设计得不好的问题。bmoathn 问能否接入 Garmin Connect。作者说现阶段不打算做客户端，他的目的之一就是启发别人做出不同口味的开关，并提到 deadmanswitch.com 有手机 App。

**谁来维护「死后系统」。** y42 说根据经验没有永远运行的数字系统，一年后怎么保证它还能用？作者说系统每年会让联系人重新确认，漏收签到邮件时他会去查服务器，还有一个健康检查地址可以接外部监控，「这是尽力而为，总比没计划好」。justauserid 和 calyhre 指出一个悖论：人走了账单没人付，开关所在的主机也会停。作者的做法是主机费提前两个月付，副手也可以代付，并建议把开关放在与主业务不同的服务商和账单账户上，比如他的开关在新加坡，而大部分网站在澳大利亚。justauserid 还设想做成端到端加密的托管服务，难点在于人走后如何解密；作者说不想处理保险和担保问题，所以不做托管。

**业务连续性要靠人。** Shank 指出这属于「业务连续性计划」（BCP）范畴，应当有由人执行、经过测试的书面流程，找已经信任且了解基础设施的人，至少每年演练一次，通知工具只是其中一环。作者说 README 里写了演练脚本和每年重新确认联系人的流程。asafel 是有付费订阅用户的独立 App 开发者，最担心的是苹果和 Google 的开发者账号都绑在个人身上；作者建议把副手加为 Apple（需组织账号）和 Google Play Console 的管理员，并在主文档里写好双因素恢复步骤。silisav 称之为「解决公交车因子（bus factor）」。

**为客户着想让人不适吗？** altmanaltman 摘出作者帖子里反复出现的「我的客户」，说这种语境下这么强调客户让他不舒服；bayarearefugee 说死后对生意伙伴毫无义务，「不再是我的问题了」。dofm 讲了不同的经历：做自由职业多年，有些客户对他去世的打击可能比家人还大，小企业的项目往往处在关键节点，已付了部分款，找替代者的成本足以让对方陷入危险；他曾试图帮助一家网页开发者心脏病突发去世的公司，开发了几个月的大功能即将上线却拿不到任何访问权限，而敦促他去帮忙的竟是那家公司最直接的竞争对手。作者则说他是做长期生意的，亲属总是第一个被通知。

**对 AI 和「太简单」的质疑。** vasco 问为什么要分享十条提示词就能做出的东西；作者说是为了启发别人思考继任计划。jubilee33 坦言自己总觉得作品不够新颖不好意思发，altmanaltman 鼓励说大多数帖子根本上不了首页，只要不刷屏就值得试试。jen729w 给所有 AI 产品同一个建议：可以用 AI 做产品，但请自己写文案，否则访客看到 AI 腔就会认定是「垃圾」直接离开；effortprogramme 也建议给网站「去 AI 味」。yieldcrv 嘲讽「Claude 自己编出来的 42 个单元测试」不能当作可靠性保证；作者说不提供托管，可靠性要靠用户按 README 的演练脚本自行验证。egamirorrim 问「现在还有人写 PHP？」，作者说 2002 年读的第一本编程书就是 Larry Ullman 的 PHP；dofm 补充 PHP 在各类流行度调查里排在 Rust 和 Go 之前，部署最简单，包管理器出奇地不糟，AI 写得也很好。此外 stevekemp 提醒 README 写着不接受 PR，但仓库仍开着 PR 功能；matt3210 调侃「你还好吗兄弟」，作者答昨天刚签到过。
