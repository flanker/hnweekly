## 文章摘要

这篇文章由 Addy Osmani、Morgan Westlee Lunt 和 Qing Wang 撰写，发表在 Claude Code 官方博客，讲 Anthropic 的 Claude Code 团队在「Claude 写了约 90% 代码」的情况下如何做代码评审。核心思路是：评审没有取消，但大部分「阅读」交给了机器，流程围绕节省人的时间和注意力来优化，同时大力投资于让错误能快速撤销。文中给出的数据是：6 月到 9 月，Claude Code 代码库合并的 PR 数量翻了一倍多，而需要回滚的比例下降了 40% 以上。

**重新定义评审的目的。** Agent 写代码后变更量暴增：Anthropic 主仓库（monorepo）每天落地的变更从 5 月的约 2500 个涨到 9 月的 3 万多个；Claude Code 本身在独立仓库里，压力同样很大。作者认为评审有两项工作：上线前发现并修复问题，以及在团队内建立对代码库的共同理解。「有没有人读过代码」只是一个不精确的替代指标，真正该问的是「这个变更可能出什么问题、哪种检查（自动或人工）最适合发现它」。评审也因此从流程末端的一道闸门，变成像写作时的拼写检查那样持续进行。目标是：Claude Code 各仓库（CLI、桌面和网页应用、移动应用）的大多数 PR 最多只需一个人参与（可以就是作者本人），同时回滚和事故不增加。他们追踪每个 PR 的人工批准数（中位数和 P95）、人工评论数、等人的时长，并以回滚率和事故率作为护栏：如果这两个数上升，说明没有省下人力，只是把时间挪到了修 bug 上。

**层层把关，而不是一道闸门。** 文章把流程分为七层：

1. **别人看之前先自我验证。** 给 Claude 可以运行的东西（测试、构建、与设计稿对比的截图），要求它展示输出而不是口头说「做完了」；再让一个上下文全新的子 agent 审查 diff。提 PR 前很多人还会跑几个内部 skill：找 bug、精简 diff、端到端检查行为。Claude Code 的创造者 Boris Cherny 估计，让 Claude 能验证自己的工作可以让结果好两到三倍。反复出现的问题会从源头修：写进 skill、加 lint 规则，或更新 CLAUDE.md（简短说明项目的技术栈、约定、目标与非目标）和由代码负责人编写的 REVIEW.md（说明在这块代码里什么算失败，比如文档的失败是「说谎」，配置的失败是「路由错」，限制吹毛求疵的数量，要求给出文件和行号作为证据）。
2. **每个 PR 都有 AI 评审。** Claude 会结合整个仓库和 PR 的意图审读 diff。研究预览上线时，内部 PR 收到实质性评审意见的比例从 16% 升到 54%；超过 1000 行的 PR 大多有发现，小 PR 大多干净。管理员可以按仓库选择 Quick、Standard 或 Deep 档位。多个 agent 并行找 bug，另一组 agent 对每条发现投票，足够多认为是真问题才会发布；纯风格和清理类意见被过滤掉。剩下的按严重程度标为 Important、Nit 或 Pre-existing（既有问题，不算作者的锅）。每条发现都必须处理：要么修，要么附理由关闭。
3. **可以阻止合并的安全评审。** 任何漏洞评审或安全评审的发现未关闭，PR 就不能合并。
4. **阻塞式自动检查。** lint、类型检查、全平台测试和构建，一个典型 CLI PR 在有人看之前可能已跑了几十项检查。PR 模板要求写明如何测试、如何撤销。
5. **按风险分级的人工批准。** 低风险（文档、文案、仅内部功能、开关后的新增改动）在自动评审和安全检查通过后无需人工批准；中风险（普通产品变更，以及缓存、自动更新器、系统提示词等敏感区域）需一人；高风险需两人。风险等级由分类器根据变更本身判定，而非看作者；第二个分类器再判断是否需要额外的人。只有仓库信任名单上的作者才能走轻量路径；agent 的批准永远不能顶替人的批准；指挥 agent 写代码的人算作必需评审者之一；批准只对特定 commit 有效，之后有无法担保的新提交需重新批准。
6. **合并队列、功能开关与渐进发布。** 合并队列会把变更应用到 main 上重跑所有检查；新行为通常先通过开关面向 Anthropic 员工开放，公开发布先进 latest 渠道，stable 渠道随后跟进。
7. **快速发现、快速回滚。** 开关无需部署即可关闭，团队有每周轮值，事故复盘会追问「本该由哪一层拦住」。作者承认还没有「指标变差时自动收紧审批」的熔断机制。

**让评审者变得更好。** 过去导致事故的 PR 及其修复和回滚，经熟悉代码的工程师确认后，构成每天运行的评测集。噪声则通过观察人们如何回应评论来衡量：修了、说错了、说是有意为之还是不重要。他们还在已知干净的 PR 上跑评审，统计会诱导出有害修改的误报。噪声在作者是 agent 时代价更高：人几秒钟就能无视一个小意见，agent 却会去修，于是又多一轮提交和评审。曾有一个 CLI PR 一夜之间经历了 50 多轮「评审—修复」。git blame 显示评审反复标记的问题中约 59% 是第一轮时就存在的旧代码。于是他们加了上限：三轮之后让作者退一步重新考虑方案；几轮之后只审新增 diff；标出一类 bug 让作者全部修掉；不重复已发过的发现。

**人留在哪里。** 决定要不要做（方向、品味和范围）、审查高风险代码（计费、自动更新器、CI 流程）、审查会被他人效仿的架构、阅读证据（测试输出、截图、评审发现），以及为结果负责。关于评审的第二项工作即知识共享，文章坦言没有正式流程：团队里没人脑中有 Claude Code 的完整模型，他们也认为没必要；想了解某一块时，就让 Claude 写一份针对那一部分的讲解，几分钟就能完成，还反映代码的当前状态。团队奉行「你合的，你负责」，靠变更小、一切可撤销、按影响范围设门槛、遥测和内部使用尽早暴露回归来支撑，并强调这不是追责。文末给出了外部团队可照搬的清单，包括 CLAUDE.md、REVIEW.md、本地 /code-review 与 /security-review、PR 模板加「测试/风险/如何回滚」、按风险分级、CODEOWNERS、合并队列、把事故变成评测集等。

## HN 评论精华

本帖 486 分、460 多条评论，是本期最热的讨论之一，整体基调相当负面：大量评论质疑「每天 3 万个变更」的意义、对 Claude Code 自身的质量表示不满、担心没人理解代码的后果，还有不少人指出文章本身读起来就像 Claude 写的。

**「每天 3 万个变更」引发嘲讽。** mixtureoftakes 直呼「我们到底在干什么？」。JackSlateur 写了个循环往 README 追加一行再提交的脚本，讽刺「每天合并的变更数」和代码行数一样毫无意义；devin 说这让他想起那篇「代码行数换了个更好的公关」；JamesSwift 调侃这周是发布了 15 万个功能，还是打了 149995 个地鼠外加 5 个新功能。_verandaguy 说作为用户他不想要一个每天在脚下变来变去的产品，「速度不是产品」。不少人以为 3 万是 Claude Code 自己的数字，steveklabnik、markbao、Tadpole9181 多次澄清这是整个 monorepo 的数据，Claude Code 在独立仓库；zeroonetwothree 补充他在 Facebook 时（LLM 之前）每天就有五万到十万个变更。cush 认为单看这个数字无法得出任何结论，取决于仓库里放的是什么，「我们以前嘲笑用代码行数衡量工程师的坏经理，现在我们自己成了坏经理」。jstummbillig 和 oofbey 则反过来好奇那剩下的 10% 代码是谁写的。

**对 Claude Code 质量的不满。** crooked-v 说这解释了为什么 GitHub 仓库有 5000 个 issue，其中约三分之一是随机的行为回归；lavezzi 贴出变更日志里「fixed」占比随时间变化的图。gonzalohm 抱怨桌面应用的按钮位置每次打开都可能不一样；enraged_camel 认为 UI 在过去半年明显改进，只是迭代太快显得变化多。stymaar、luisgvv 吐槽滚动卡顿、思维链显示等老 bug 一直没修。K0balt 指出 UX 的高频「优化」是隐藏的反模式，AI 在注意力流和功能发现这类体验评审上很糟糕，开发 10 倍提速后反而需要更多 UX 人员。

**没人理解代码会怎样？** 这是讨论中最有深度的一条线。status_quo69 质疑文章说「需要了解时让 Claude 写讲解」并不是知识，只是一种搜索，质量取决于你搜得好不好。jonahx 认为这是问题的关键，代表软件信任模型的巨变：系统出了没人能搞清的严重 bug 时，没有任何人脑中有因果模型可以依靠，一切都押在「Claude 总能找到并理解系统的正确切片」这个新不变量上，「你成了一艘回收来的外星飞船的主人」；他也承认很多大型遗留系统早就类似，只是把 Claude 换成了「今年碰巧在维护它的人」。peab、dmd 指出 Google 或银行这类系统本就没人能装进脑子；aturek 反驳说遗留代码背后至少有带意图的人脑，可以建模和推测，而 LLM 盲写的代码没有意图可循；TeMPOraL 认为那就像研究自然界一样，用科学方法去理解没有人类意图的代码。marcindulak 举了一个具体例子：Claude Code 公开仓库中，维护者转贴了 Claude 写的说明，称 issue 只因缺少信息才被机器人自动关闭，但实际上所有 issue 都会因无活动被定时关闭，除非攒够点赞，说明「让 Claude 讲解」并不总能反映代码现状。tripleee 说他用 Opus 完全 vibe coding 了一个 1.5 万行的工具，读完也不知道它是怎么架构的，测试也不敢信，越来越不敢改。avinoth 把这比作 Google 的基础设施博客：只适用于他们自己，Anthropic 能这么做是因为 token 几乎无限，其他团队仍需理解代码，否则就会变得永远依赖 token 供应，而这正是 AI 实验室想要的。

**逐行评审还要不要？** dylanhouli 说他仍然忍不住逐行评审，因为总能发现冗余、重复、过度复杂的架构。stillpointlab 建议他开一个完全 vibe coding 的低风险副项目来建立信心，引发与 troupo 的长篇争论：troupo 认为 LLM 会持续产生重复代码和糟糕架构，任何「驾驭 agent」的技巧都修不好，低风险项目也解决不了根本问题。zeroonetwothree 分享了在一个约一千万行、大部分 vibe coding 的项目上工作数月的体会：agent 修 bug 只修一处，其他地方同样的问题要等你发现；面向用户的文字依然别扭；它不懂什么信息对人重要，比如不理解「免费」和「0 美元」在人眼里的区别；他后悔走上这条路，但已无法回头手工维护。72deluxe 说他 vibe 出了一个有用的工具，但完全不知道它怎么工作，唯一的「维护」方式是交给另一个 LLM 解释。bpeng2000 观察到 AI 在大代码库里倾向于为新功能另起炉灶，因为复用和泛化旧代码成本更高，这些「新轮子」不断积累并相互缠绕。

**安全、合规与成本。** vavkamil 担心「附个理由就能关闭安全发现」，关键漏洞的误报判定仍应有 AppSec 参与，而且官方安全评审 Action 的 README 明说未针对提示注入加固。gaal_dornick 问「最多一个人参与、且可以是作者」如何满足 SOC2 要求另一人评审的规定，以及如何防范内部人员恶意提交；llama052 认为大概并不合规，只是审计比较宽松。afro88 指出「开关后的新增变更」只在开关关闭时是低风险，打开那一刻风险才真正出现。Otterly99 认为整条链中最薄弱的一环是决定哪些变更送给人工的分类器，它是如何校准的？rileymichael 抱怨 Claude 代码评审产品原先标价每次 15 到 25 美元太贵；warkdarrior 算账说年薪 15 万美元的工程师评审 30 分钟就值 36 美元，markbao 说他们每月花几千美元做 AI 评审，相比工程师三分之一时间花在评审上仍然划算。多人分享自建方案：walthamstow、a3nz3g、abalgir 都用不同厂商的模型交叉评审（Claude 写、Codex 审，或反过来），abalgir 还让评审者自建测试场景账本、主动反驳「已完成」的说法；NorthSouthNorth、tills13 在 GitHub Actions 上自建评审机器人，tills13 说 bugbot 小团队每月要 1000 美元，自建大约 100 美元。chris_money202 指出，需要编译、工具链 200GB、集成测试要跑几个小时的项目，根本无法照搬这种快速反馈循环。

**文章本身像 AI 写的。** mk12 说听说 Anthropic 员工不用 AI 写对外文章，但「大部分路径是自动化的；人的注意力投向风险所在」这种句子正常人不会这么写；paimapi 和 typesanitizer 都说 Pangram 检测出大段 AI 生成内容。drewbeck 说这种每句都在强调的语气让人疲惫，wannabe44 形容「每一句都像在推销」。jazzyjackson、cjkhowes 等人则认为长期与 AI 打交道的人也会染上「Claude 腔」，几位母语非英语的读者担心自己的文字会被这种风格同化。

**少数正面声音。** drooby 说他每天用 Claude Code，觉得产品流畅好用，他们在用一种新方法写好软件，「这个社区已经和现实脱节了」。cheema33 认为大型组织里本来就没人掌握完整心智模型，Anthropic 的做法相比现状是升级。piro0919 说在他的经验里 Claude 代码评审发现的问题比人工评审还多。mcbishop 则欣慰地指出，连 Anthropic 也认同「会被他人效仿的架构」最好交给人来定。
