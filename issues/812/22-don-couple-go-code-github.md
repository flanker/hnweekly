## 文章摘要

这是 Iain Cambridge 2026 年 9 月 27 日发表的一篇短博客，讨论 Go 模块路径的一个老问题，并给出了用自定义域名做"虚荣导入路径"（vanity import path）的具体配置。

**Go 的命名方式是把双刃剑。** 作者先肯定了 Go 的一个好设计：代码的命名空间就是获取代码的位置。如果你把代码放在 `github.com/thetrueares/boneclone`，那么导入语句就写 `import "github.com/thetrueares/boneclone"`，Go 会用 git 去拉取。这样一眼就知道去哪里给开源库报 bug，也不需要一个中心化的包管理系统就能方便地获取和分发库。对很多人来说，模块路径就是 git 托管地址本身。但作者认为这样做有弊端，应该用自己的域名。

**问题：代码被耦合到托管商上。** 用托管地址做模块路径，意味着你的代码和托管商绑在了一起。如果要把 git 托管从 GitHub 迁到 GitLab，你就得改代码，否则拉到的还是旧版本。迁移成本高到一定程度，你就干脆迁不动了，"代码真的和 GitHub 耦合了"，作者说这听起来很荒唐，却几乎是 Go 社区的默认做法。他举了一个亲眼见过的例子：一家公司同时在用 GitLab、GitHub 和 Azure DevOps，因为改代码位置的工作量太大，他们"没时间"，于是同时在三个平台上运营，付三份托管费。这也是作者开发 Boneclone（一个在多个 git 托管平台之间同步骨架代码的工具）的原因。

**解决方案：自定义域名。** 像 `go.iain.rocks`、`go.uber.org`、`go.mongodb.org` 这样的自定义域名，需要换托管时只要改域名指向即可。比如 `go.iain.rocks/boneclone` 指向 GitHub 上的仓库，哪天迁到 GitLab，用户的安装命令完全不用变。作者认为每个用 Go 的商业软件团队都应该用自定义域名给内部库和包做命名空间，这是避免无谓耦合的简单办法。

**配置示例。** 文章最后贴出了作者自己的配置。Nginx 部分的思路是：检查查询字符串里是否带 `go-get=1`；如果没有，说明是人在浏览器里访问，直接 301 永久重定向到 GitHub 上对应路径；如果有，说明是 Go 工具在请求，就返回一个静态 HTML 文件，另外配好 Let's Encrypt 的证书和 HTTP 到 HTTPS 的跳转。那个 HTML 文件里只有两个 meta 标签：`go-import` 告诉 Go 工具该模块路径对应哪个 git 仓库；`go-source` 告诉 pkg.go.dev 之类的工具源码目录和文件该链接到哪里。

## HN 评论精华

本帖 326 分、约 180 条评论。文章很短，但讨论相当热烈，基本分成两派：一派认为改托管时搜索替换、或在 go.mod 里加 `replace` 就够了，文章小题大做；另一派有真实迁移经历，强调问题远比看上去麻烦。还有不少人从根本上质疑"自定义域名"是否真比 GitHub 更可靠。

**"搜索替换不就行了？"** handoflixue 的疑问代表了很多人的第一反应：所有地址都指向 github.com，搜索替换应该是最简单的情况。dewey 说在 go.mod 里写一行 `replace github.com/example/example => gitlab.com/example/example` 就一切照常，"这是对无关紧要之事的过早优化"；lelandbatey 补充还可以用 GOPROXY 把一切都指向自己的制品缓存，"模块名即网络路径只是方便的约定，不是工具链的限制"。serbuvlad 也说在极少发生的事件之后跑一次 sed 算不上严重问题。

**亲历者的回答是"非常痛苦"。** mort96 是这一派最有说服力的声音。他参与过一次迁移：一个分布在大量 git 仓库里的庞大 Go 代码库要搬到另一个 git 托管上，一组人花了好几周。不同项目依赖同一批内部库的不同版本，而目标是迁移后系统"完全一样"，所以不能顺便升级依赖，只能为每个被依赖的提交单独建分支，做一个改了 URL 的版本。结果是 bisect 失效，想构建任何代码的旧版本都要费很大功夫。他后来举了一个具体例子说明为什么数量会爆炸：libfoo 有多个版本，authservice 依赖 1.2.0，apiservice 依赖 1.3.0，你改完三个仓库的主干后，还得从 libfoo 的 v1.2.0 和 v1.3.0 标签各拉分支改一遍；如果 apiservice 还依赖 authservice 的旧版 v2.3.7，而 v2.3.7 又依赖 libfoo v1.2.5……三个仓库就要做七次搜索替换，规模一大数字就很吓人。对于"在 go.mod 里 replace 就行"的说法，他反问："那你的所有源文件里就永远留着指向废弃基础设施的 URL？"他强调 Go 和 Java 的 `com.sun` 不同，后者只是个标识符，而 Go 的工具链真的会去请求那个 URL、解析返回的 HTML 再 git clone，所以留着旧地址就是在源码里留死链，万一那个地址落到不可信的人手里，工具还会信任它的响应。MadVikingGod 也写了一个 A→B→C 依赖链的入门示例，说明无论怎么做，都无法在不改动所有依赖的情况下继续构建旧版本。shieldagent 说他们在组织改名后就踩了坑：`replace` 能覆盖自己的模块，但传递依赖里的旧 github.com 路径照样让构建失败。

quectophoton 补充了一个很多人不知道的细节：`replace` 只在顶层模块生效，依赖里的 `replace` 一律被忽略。如果你依赖的第三方框架用了有漏洞的 `golang.org/x/net/http2`，你没法在那个框架的仓库里用 `replace` 修，只能在主模块里修。他还说 Go 工具链对 GitHub 和几家主流托管有硬编码的特殊处理，你自建 Forgejo 时才会发现"为什么 GitHub 上能用、我自己的就不行"。他的结论是 Go 似乎只在乎单仓库（monorepo），一旦涉及分支、镜像或私有模块，工具就处处和你作对。

**自定义域名真的更可靠吗？** 这是另一条主线，反对声音不少。SenHeng 的评论得票较高："GitHub 几乎是永恒的，你的自定义域名会在你不再续费时消失，对开源开发者来说这比 GitHub 消失的可能性大得多。"st3fan 说公司倒闭时域名一定是最后才会想到的东西，下一个注册者就能接管别人依赖的代码，其他生态已经发生过很多次。dolmen 举了 deepcopy 的例子：作者九年前就消失了，这个包至今仍被大量使用，至少 GitHub 是个稳定可信的分发点。sleepybrett 说自己的域名已经用了 25 年，但他终有一天会死，家人不懂他做的事，域名会过期，模块就永远丢了。p4bl0 提醒域名也并非完全可控，并给出了一个 VeriSign 单方面决定删除成千上万域名的新闻链接；hnarn 解释说那涉及一种可以不拥有二级域名、直接从注册商购买三级域名的旧机制，由于用的人太少正在被淘汰。PunchyHamster 吐槽："现在你耦合了两个你不拥有的服务，恭喜你把事情搞得更糟了。"支持者也有回应：mkj 说照软件行业的发展速度，GitHub 迟早会像 SourceForge、Travis CI、MySpace 那样没落，他的个人域名已经用了 23 年；epwr 认为对公司来说自己的域名风险更小，如果托管商倒闭、域名被别人买走，你得在毫无准备的情况下做大规模重构，而自己的域名会一直持有到公司关门，那时也没人跑你的代码了；throwawayffffas 一针见血："域名出问题你还能修，GitHub 出问题你只能盯着状态页。"

jerf 从更抽象的角度给出了一个高赞观点：命名一个包总要依托某种命名空间，而所有命名空间都是人造的，都可能失效。文章的意思不过是"这个命名空间会失效，换一个吧"，但新的照样会失效，而且几乎肯定比 github.com 失效得更早。既然不存在不会失效的命名空间，唯一能做的就是保持韧性，并相信未来遇到问题的人能解决这个本可解决的问题。mfro 和 bloppe 反驳说文章讲的并不是命名空间失效，而是把命名空间和托管商解耦，换托管时改 DNS 比迁移库和引用简单得多；dcreager 说他换托管跟可靠性无关，而是品牌问题，他想掌控代码的身份。

**真正的出路：vendoring、代理和内容寻址。** 不少人认为该关心的是可复现构建。racingmars 说无论托管在哪，都不要假定依赖明天还在，"永远 vendor 你的依赖"；tugback 说他们就遇到过一个私有 GitHub 依赖消失，是 vendoring 救了他们。otterley 问"我们当初为什么不再 vendor 了"，jeremyjh 的回答是工具默认不这么做，锁文件省存储、克隆更快；throwaway894345 则说自己 2012 年起用 Go，想不起 vendoring 比普通模块更管用的时候。多人提到 Go 默认走的 proxy.golang.org 缓存代理本身就缓解了源站消失的问题。0xbadcafebee 建议更进一步：把这个域名指向一个制品仓库，从代理模式起步，以后再锁版本、校验哈希、接 SSO，这将成为新安全形势下的基本配置。Groxx 希望 go.mod 里直接带上内容哈希，让人能从任何代理拿到已知可信的版本；cyberax 也认为 go.sum 已经有哈希，只差内容寻址的获取方式，下一步是支持声明"从此以后 github.com/company/x 就是 company.com/x"。lewo 提到 Nix 和 Guix 的做法：源站失效时回退到 Software Heritage 的存档。verdverm 透露了一个趣闻：Go 团队在帮 CUE 设计模块系统时说过，如果能重来，他们会用一个注册中心，CUE 最后用的是 OCI 镜像仓库。unscaled 和 12_throw_away 则带点讽刺：Go 当年说服了粉丝"别的语言用官方包名都是错的"，现在又让大家各自搭 nginx 做转发，再配上推荐的缓存代理，"正在从第一性原理重新发明传统的包索引"。

**关于配置本身的小提醒。** 0xCMP 和 blackjpi 都指出示例里的 301 永久重定向有隐患：浏览器会永久缓存 301，以后想把人类访问者重定向到别的托管时，访问过的浏览器仍会跳到旧地址，何况示例里也没有设置任何缓存控制头，blackjpi 说自己就被这个坑过，所以不会在这里用 301。globular-toast 问能否只靠 DNS 而不用跑一台 Web 服务器，andreashaerter 分享了用 Hugo 模板生成静态虚荣导入页面的做法，并自嘲"我知道把它托管在 GitHub 上很讽刺"。mort96 和 someonebaggy 还给了一个非库项目的省事做法：go.mod 里直接写 `module Frobnicator`，或者用 example.com 前缀，完全不带托管地址，只是工具和同事都会推着你去用 Git 托管的 URL。
