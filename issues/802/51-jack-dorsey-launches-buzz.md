## 文章摘要

（注：runtimewire 原文只抓到标题，正文抓取失败；以下内容基于 Buzz 官方仓库 README、官网及 HN 讨论整理。）

Jack Dorsey 与 Block 发布了新项目 Buzz，一个可自托管的团队工作空间，把团队聊天、AI 智能体协作、代码评审、工作流和 Git 托管统一到同一套事件日志里。项目的自我描述是"一个人类与智能体共同构建的工作空间，跑在你自己拥有的 relay 上"，官网口号则是"你的人、你的智能体、你的项目，都在一处"。代码以 Apache 2.0 许可开源在 github.com/block/buzz。

技术选择是这个项目最具辨识度的部分：Buzz 建立在 Nostr 协议之上，以一个可自托管的 Nostr relay 为核心。每一条消息、每一次表情回应、每一个工作流步骤、每一次评审通过、每一个 Git 事件，都是同一条日志里的一个经过密码学签名的事件。后端是 Rust 微服务（Axum 写的 relay，配 Postgres、Redis 和 S3/MinIO），桌面端用 Tauri + React。Git 侧走 NIP-34 的 patch 事件，并集成了 git-credential；媒体托管用 Blossom 协议。部署方式既可以用 Docker Compose 自托管，也可以直接下载 macOS / Linux / Windows 的打包版本。

Buzz 最核心的产品主张是把智能体做成"一等公民"而不是受限的 bot：每个智能体拥有自己的密钥对、频道成员身份和审计轨迹，与人类员工共享同一套身份结构。它们可以开仓库、提交 patch、评审代码、跑工作流、编辑画布、编排其它智能体、加入语音会议、创建频道。官方说明核心功能目前已可用，工作流审批和移动端还在开发中，信任网络（web-of-trust）与推送通知尚在规划。

在 HN 上这条帖子拿到了 376 分和三百多条评论，但整体氛围相当分裂。支持者认可"人机混合协作需要新的原语"这个判断确实抓住了真问题；怀疑者则集中在三点：Nostr 在企业聊天场景是否属于强行套用、智能体拿到跨频道视野后权限模型会不会崩、以及一个由科技名人主导、大量借助 AI 生成的项目能否长期维护。另有不少人纯粹在讨论"Buzz"这个撞上 Google Buzz 的倒霉名字。

## HN 评论精华

- **rvz** 补全了官方来源（Jack 的推文、buzz.xyz、block/buzz 仓库）。**giancarlostoro** 顺手抛出一句被高赞的调侃："每次看到有人做 GitHub 替代品，代码却托管在 GitHub 上，我都会笑一下。这恰好说明取代 GitHub 不只是取代代码托管。"

- **muglug**（Slack 员工，声明仅代表个人）给出了整场讨论里最专业的一条技术批评：让智能体看到你和同事看到的一切确实很酷，但当你需要把某些东西设为对某些人私有时，你就不希望多人共享的智能体泄漏数据，于是你不得不编写并维护关于智能体能访问哪些具体资源的复杂规则集。相比之下单人智能体要直白得多——它代表一个用户行事，问题只剩"确保它不把私有数据外泄到共享空间"。

- **another-dave** 认为 Buzz 的设计恰好回应了这点：智能体是独立的一等用户而非应用集成，那就按普通 ACL 处理，不必区分人和机器。**jaggederest** 指出这没解决核心问题：用户和 Claude 对话时，Claude 能看到什么？如果它能读到 super-secret-payroll-details.md，它可以跟任何人讨论吗？"难道要在 Claude 内部再放一层 ACL，求它别告诉大家自己被低薪了？"

- **another-dave** 提出一个具体方案：不要装一个 god-mode 的全局智能体，而是跑十个各有上下文和 ACL 的实例，让智能体的权限取其所在全部频道中最低权限用户的交集——你想把某个 bot 加进"高管奖金讨论"频道时，系统会告诉你"不行，因为 AliceBot 同时在 #intern-onboarding 里和 Johnny 共处，而 Johnny 没有这个频道的权限，要新建一个 bot 吗？" **jaggederest** 的回应很干脆："抱歉带来坏消息：那还是巨大的 ACL 和权限问题，只是多了几个步骤。"

- **teach**（基础设施工程师）提供了少见的"这真是我的痛点"视角：他们团队重度使用 LLM 写代码和评审 PR，护栏做得很好、输出质量很高，但让人和智能体一起对话这件事目前极度碎片化——"那个在我本地 Cursor 里、握着全部上下文的智能体，没法参与 Slack 上关于一个主要由它撰写、我签过字的 PR 的讨论。这是我们每天面对的真实沟通问题，早晚有人把它做好，然后我会请领导给他们很多钱。" 面对"为什么不给 Cursor 装个 Slack bot"的反问，他指出障碍是商业性的：Slack 想卖自己的 AI 集成产品，所以既把这条路做难，更重要的是它违反服务条款——而他们付的钱多到 Slack 一定会注意到那种量级的索引行为。

- **Gecko4072** 说出了很多人的第一反应："现在看到新软件项目，我只会想它有多大比例是智能体做的，以及随之而来的不可靠和易被抛弃。十年前这个产品会有一个已知的质量水准。" **horsawlarway** 反驳说绝大多数软件本来就是这个结局，Google 自己就在 2010 年推过一个同样社交主题、只活了 16 个月的 Google Buzz，"要么找到 PMF，要么找不到，代码质量跟它两年后还存不存在关系没那么大"。**AlienRobot** 用六行伪代码总结了他担心的循环：AI 生成函数 → AI 生成测试 → AI 改函数 → 测试挂了 → 删掉所有测试 → AI 重新生成测试。

- **grim_io** 直白地问："抛开营销废话，这不就是聊天室里的机器人吗？是我疯了吗？" **serf** 给了一个建设性的回答："但现实是每个聊天室机器人集成都做得半吊子，而做得好的那些又强迫你用要么麻烦、要么观点极强、要么缺功能、甚至缺最基本安全隐私姿态的服务。这里确实有把它做对的空间。我只是怀疑做成的人会不会是 Dorsey。"

- **rsstack** 挑出文章的 ELI5 摘要开涮："Buzz 是一个开源、自托管的工作空间，用签名的 Nostr 事件把团队聊天、AI 智能体和 Git 托管结合起来，让团队掌控自己的数据。"——"对五岁小孩的期待很不一样啊。" 这条衍生出全场最长的一条离题支线，从 The Office 的剧集考据一路追到爱因斯坦和卢瑟福的名言归属。**mjg2** 补刀："如果五岁小孩都懂签名的 Nostr 事件，成年人还有什么希望？我想下车了。"

- **dewey** 从实际做过 Nostr 项目的经验出发下判断："我最近也做了个支持 Nostr 的项目（纯粹是为了玩），但把它用在团队聊天这种场景上感觉非常勉强，它在解决一个团队聊天从来没有过的问题。" **verdverm** 的批评更技术：ATProto 的私有数据方案在企业所需的粒度上不够用，很多必需能力（比如群组）终究要建在 app view 里从而事实上中心化，"ACL 比 IAM 的历史落后两代"；他还透露自己基于 ReBAC/SpiceDB 做过 PDS 分支原型并在第一次 Private Data 工作组上做过演示，"Bluesky 没人到场"。

- **jacobgold** 提出另一条路线：Slack 之所以存在是因为 IRC 不够用（没有原生的频道历史和搜索）；要让智能体繁荣，Slack 要么真正用协议开放网络，要么最终被取代。他希望 Slack 拥抱基于 AT Protocol 的聊天系统，用户用域名 handle 登录，智能体用 @agent1.yourname.com 这样的 handle，全部在自己掌控之下。

- **_verandaguy** 提出了一个更根本的质问："凭什么帮智能体繁荣是 Slack 的责任？我在整个行业都看到并亲历了这种倒转——我们必须为 AI 改造自己的工作流。工具不该是为你服务，而不是反过来吗？" **Jare** 从竞争现实回应："如果世界转向 AI 驱动的工具而 Slack 不配合，它就不再服务这个世界，会被落下。你想要聊天里的 AI 集成而 Slack 不帮你实现，那 Slack 就没有为你服务。" 但他也承认，AI 本身大概不是一时风潮，而互操作的具体方式（MCP、CLI、agent、tag……）很可能是。

- **jillesvangurp** 分享了一线试错记录：他们先用 Slack 做 bot，能跑通但每加一个新 bot 都要重新调一堆权限，很痛苦；然后转向自托管，试过 Matrix（端到端加密太严格，反而妨碍与 bot 共享信息），几周前换到 Zulip，创建 bot 用户和自动化都很简单。他还提到一个耐人寻味的信息：Zulip 的核心团队刚被 Anthropic 招走，"Jack Dorsey 抢先发了公告，但我猜 Anthropic 大概有非常相似的计划"。

- **darth_avocado** 的批评火力集中在 Dorsey 本人："作为 Block 股东看到这个我会很生气。他多年来一直在 Tidal、区块链、Weebly 这些支线任务上兜圈子，同时忽视核心客户的需求。Toast 是家 200 亿美元的公司，Block 收了 Afterpay 之后也就 500 亿，而 Square 本该拿下近 90% 的市场份额，这很难看。" **jjfoooo4**（Block 员工）纠正了一处事实：Cash App 不是收购来的，它源自当年 Square 内部的一次 hackweek。

- **themgt** 贴出仓库里的产品截图并称之为"林奇式恐怖"：#engineering 频道里"团队，新方向——我们把原型迁到 Flutter"，然后人类和取着 Honeybot 之类可爱名字的 bot 们用满是表情的俏皮语气对话，"我搞定了物理，UI 外壳交给 @Honeybot？"。**Lalabadie** 眼尖地指出所有消息的时间戳都是 5:42，说明这是用种子测试数据摆拍的或纯 mockup。**hahahaa** 的解法很实用："系统提示里让它别这么说话就行。再加一个爱抱怨的资深工程师智能体，专门反对频繁换技术栈，那会很好。"
