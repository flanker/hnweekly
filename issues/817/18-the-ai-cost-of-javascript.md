## 文章摘要

Nolan Lawson 不满足于「某框架更适合代理」的主观说法，于是让 Opus 5.5 按同一份需求构建 Pokémon 信息网站，比较多种 JavaScript 框架的开发时间、token 用量、代码量以及 Lighthouse 表现。实验提供规范符合性测试，并尽量配置各框架官方 MCP 或技能，但不强制客户端或服务端渲染，也不要求特别的性能优化。大多数框架重复五次取中位数，Angular 有两次未得到可测应用，部分指标因此只计算三次。

这组结果中，Hono+htmx 和 Astro 的构建报价较低，分别约为 2.67 和 2.76 美元；Astro 时间中位数为 8.2 分钟，客户端 JavaScript 传输量也很小。报价按工具显示的 API 价格计算，不等于作者套餐的实际额外支出。新框架知识不足、反复查迁移指南、代码冗长和代理偶然绕路，都可能改变成本。

作者反复强调实验边界：这是偏内容展示的小应用，不代表复杂编辑器、实时协作或大型业务系统；初始加载指标也更有利于多页和服务端渲染方案。代码行数只是可维护性的粗略代理，五次运行也不足以消除随机性。文章提供的是可复查的比较方法和一个具体样本，而不是证明所有团队都应选择同一个框架。

## HN 评论精华

- **场景决定排行榜的意义。** skrebbel 指出 Astro 原本就面向内容驱动网站，希望看到复杂实时交互版本；Aozora7 则建议测试带复杂验证规则的业务表单。
- **初始成本之外还有长期成本。** neya 认为团队熟悉程度、安全记录和长期维护能力，可能比首次生成节省几美元更重要。
- **约束未必是坏事。** alex_suzuki 回忆 Angular 的统一结构曾降低多项目切换的认知负担。它与小应用中的冗长成本可以同时成立。
