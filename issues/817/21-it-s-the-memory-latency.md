## 文章摘要

Pivot 的这篇性能分析从一个常见误会切入：操作系统显示 CPU 使用率 100%，只说明任务持续占用处理器，并不代表执行单元一直在完成有效指令。若数据不在缓存中，CPU 可能花大量时间等待 DRAM。作者用高基数 GROUP BY 演示：ClickBench 的约 9,900 万行包含约 1,700 万个 UserID，直接逐行更新一个巨大哈希表，会频繁访问远离缓存的数据。

实验在 AMD EPYC 9124 服务器上限制为单核，并观察热运行和硬件性能计数器。朴素方案热运行约 3.6 秒；改为先按哈希高位分到 4,096 个分区，再逐个聚合小哈希表后，热运行约 2.7 秒。虽然总执行操作更多，但小工作集更容易留在缓存，作者记录的按需 DRAM 读取量也由约 4.5 GB 降至约 1.5 GB。

文章的核心经验是，有时多做一些便宜的指令、换掉昂贵且串行的内存等待，比单纯减少代码步骤更有效。预取、内存级并行和多核处理还能进一步优化，不过文中只详细展开分区聚合。所有速度和计数器结果都属于作者的特定机器及查询，不能直接推广成通用数据库排名；不同 perf 运行本身也有时长差异，本文未复现实验。

## HN 评论精华

- **数据布局仍是基础能力。** boricj 描述在资源有限的嵌入式芯片上使用内联分配、SAX 式处理及对象池的经验，强调用实测证明硬件友好的设计能显著减少开销。
- **抽象与工程目标需要取舍。** MisterTea 认为现成游戏引擎对「做出游戏」通常已足够，不应要求每个团队重写底层；这提醒读者把局部性能收益放回产品成本中判断。
- **不要把经验写成普遍结论。** jordand 认为年轻开发者较少关注底层性能，这是其行业观察；评论没有给出能证明整个行业技能变化的调查。
