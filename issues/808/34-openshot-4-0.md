## 文章摘要

OpenShot 是历史悠久的开源跨平台视频编辑器（GPLv3）。这篇由项目负责人 Jonathan 撰写的发布公告介绍了 4.0 版本，作者称这是项目历史上最大的一批创作工作流升级。

**新的调色视图（Color View）**。这是本次发布的重头戏之一。它把大预览窗口、片段属性、色轮和实时示波器组织在一个专用界面里。入口很轻量：右键点击视频片段选择 Look > Adjust Colors，OpenShot 会自动添加新的 Color Grade 效果并打开相应工具。这个效果同时覆盖校色和创意调色：曝光、对比、色温、色调、高光、阴影、饱和度、自然饱和度等实用控制，用于修正欠曝、去除偏色、找回高光或统一多机位素材；再往上则有针对全局、阴影、中间调、高光的独立色轮，以及四条可编辑曲线（整体加 RGB 三通道），曲线控制点和手柄可直接拖动，支持平滑的贝塞尔调整。它还支持行业标准的 `.cube` LUT 文件，并带有强度控制，让你把 LUT 混入已校正的画面而不是全强度套用。整个 Color Grade 效果都可以打关键帧——色轮、曲线、校正参数、LUT 强度和总体混合比例都能随时间变化。

**专业示波器**。4.0 加入了亮度波形图、直方图、RGB Parade 和矢量示波器，随播放头移动实时更新。每个示波器都带一个区域工具：在人脸、天空、墙面或产品上画一个框，示波器就只分析那一部分画面。矢量示波器还带肤色参考线，方便发现偏色。菜单里另有 Auto Contrast、Lift Shadows、Warm Up、Boost Color 等预设作为快速起点——它们用的是同一个可编辑的 Color Grade 效果，所以是起点而非一键滤镜。用户手册还新写了一整章讲色彩。

**新的录制视图（Recording View）**。可以直接把麦克风、屏幕、摄像头和系统音频录进项目。关键在于**每个启用的源都是独立的媒体文件和独立的时间轴片段**：麦克风与系统音频分开，摄像头与屏幕录制分开，录完可以单独修剪、调音量、裁剪画中画而不影响其他源。屏幕加摄像头组合录制时可自动生成圆角画中画布局。录制过程中有实时反馈（麦克风电平、摄像头预览、临时片段实时出现在时间轴上）。还能一边预览已有项目一边录麦克风或摄像头，适合配音、解说和教学；右键片段选 Audio > Record 会自动跳到片段开头并选好下方轨道。选 No Track 则只把成品放进项目文件不上时间轴，适合先录多条再剪。录制文件存放在项目的 assets 目录里。Windows、macOS、Linux X11 和带 PipeWire 的 Linux Wayland 都有平台原生录制路径。

**10 个新效果**。音频可视化效果能把声音转成波形、填充波形、条形、放射图案、频谱、粒子和 VU 表等动画，官方给出的性能测试称所有模式都远高于常见的 24/30/60 FPS 项目帧率，最吃力的模式也超过 170 FPS，而条形、相位示波器和 VU 表超过 1000 FPS。Beat Sync 把音频能量转成随节拍和响声反应的色彩层。此外还有 Film Grain（含 35mm Fine/Classic/Gritty、16mm Classic、Super 8、High ISO 等预设）、Denoise Image、Shadow、Glow、Displacement Map（做水波、热浪、折射玻璃）、Timer、Color Grade 和 Object Mask。

**本地运行的 AI 抠像**。新的 Object Mask 效果让你在主体上点几个正样本点、在周围点几个负样本点，OpenShot 生成选区预览并跟踪整个片段。公告特别强调**这个流程完全在本地运行**：使用可按需下载的免费机器学习模型，包括转成 ONNX 格式的 YOLO、EfficientSAM 和 Cutie，由 libopenshot 和 OpenCV 在本机执行——没有云处理要求、没有 AI 账号、没有 AI 订阅，素材不需要上传到远程服务。生成的蒙版可作为效果显示，也可复用为 Blur、Pixelate、Color Grade 等效果的蒙版源。

**完全原生的时间轴**。4.0 彻底告别了旧的基于 Web 的时间轴组件，片段、转场、关键帧、轨道、标尺、菜单和交互全部改由原生 Qt 时间轴处理。带来的改进包括更平滑的缩放、更小缩放级别下仍可见的效果图标、按源宽高比排布的缩略图间距，以及可直接编辑的时间码（点击标尺时间码输入新值回车即可移动播放头）。

**性能**。相比 3.5.1，基准测试中 Blur 效果快了 61.8%，Sharpen 快了 12.8%，时间轴渲染快了 3.4%（带变换的测试为 5.1%）。作者特意解释了为什么时间轴那几个看似不起眼的百分比很重要：时间轴几乎触及编辑会话的每一部分。

**现代化基础**。扩展的 Qt 6 与 PySide6 兼容性、桌面 portal 集成、高 DPI 缩放与窗口行为的大量修复；代码库还加入了面向 Android 的兼容性基础（文件访问、渲染、Qt 绑定、大 ARM64 内存寻址），但公告明确说明 **Android 不是 4.0 的支持平台，也没有发布日期**。底层的 libopenshot 和 libopenshot-audio 都到达了 1.0.0 版本。此外还有片段菜单重组（Transform / Look / Audio / Speed / Motion 分组）、新的相机运动预设、Focus Wipe 与 Blur Wipe 预设、字幕编辑改进、动画标题可导出 MP4、Blender 5.x 兼容性修复、EDL 与 Final Cut Pro XML 导入导出的兼容性修复，以及面向 TikTok、Instagram、Facebook、Snapchat、LinkedIn 的现代导出预设。

公告末尾特别感谢了 Blender 基金会——文中大量截图使用了 Blender Studio 的开放电影《Spring》和《Sprite Fright》作为测试素材——以及社区成员 Raffi。帖子在 HN 拿到 602 分和 138 条评论。

## HN 评论精华

**最大的争议点：一个开源项目官网上的 209 个广告追踪商**

这条线索的热度超过了软件本身。`akrauss` 开场：一个名字以「Open」开头的东西，在 `.org` 域名上挂广告技术 cookie 横幅？不看了。`iLoveOncall` 讽刺道：「拜托，他们只把你的数据给了 210 个『合作伙伴』而已。」`woadwarrior01` 说这份 209 家广告商的名单「令人厌恶」。

反击同样激烈。`bonoboTP` 提醒 Open 指的是开源（GPLv3）。`TheChaplain` 说「那是你的损失」，并认为开源开发者想挣几个钱不是什么坏事。`mogwire` 更直接：「典型的 FOSS 伪君子，因为『免费』软件得有人买单而生气。」`touwer` 反问：「你为 FOSS 做过什么？」`prmoustache` 给出了最实际的解法：从发行版仓库或 Flathub 装就好了，永远不用访问官网。

但 `iLoveOncall` 的追击有力：这是靠捐赠资助的自由开源软件，不是营利公司；而且很讽刺的是，**它那个既不完全免费也不开源的竞争对手 DaVinci Resolve 既没有 cookie 横幅也不给你设任何 cookie**。`sejje` 建议装 AdGuard DNS 或广告拦截器，说自己没看到广告；`woadwarrior01` 解释说他有拦截器，对方看不到横幅很可能是因为身处欧盟之外，数据在被静默共享——欧盟辖区内要求「知情同意」，所以才有那个横幅。

**「跟 Premiere / Resolve 比怎么样」引发的社区火药味**

`bewareofscams` 问了个看似合理的问题：这跟 After Effects、Premiere Pro、DaVinci Resolve 比怎么样？他自己给了答案：「我很确定这东西解决了上述软件一半的问题，而且只做好了一半。」

`Matl` 回怼：「我很确定你自己没试过。我也很确定你提到的软件要贵得多，或者至少不开源。这让我很确定你的评论毫无用处。」`bewareofscams` 澄清他用过他提到的那些、正因为没用过这个才来问，不需要「但我们是 FOSS」的自鸣得意评论。`Matl` 随后给出了实质回答：他自己在 Linux 上付费用 DaVinci Resolve Studio，那些软件显然功能更全更精致；但 OpenShot 明显更容易上手，能满足休闲剪辑需求，如果想再进一步又要保持自由软件，Kdenlive 是更好的选择。他认为原评论无用的地方在于「这读起来像一个美国人说『我打赌我们的 GDP 比瑙鲁大』——重点是什么？你已经知道答案了。」

这句类比把讨论带向了一段离题的欧美互嘲（`throwthrowuknow` 笑称像是两个不同欧洲口音的人互相指控对方是美国人，`1attice` 提议搞个「非美国人证明平台」）。

严肃的横向比较则由其他人补上。多位用户（`bonoboTP`、`noir_lord`、`liotier`、`Matl`）反复推荐 Kdenlive。`noir_lord` 的评价最具体：Kdenlive 近几年进步显著，而且是以你看不太出来的方式——它曾有一段极不稳定、频繁崩溃的时期，团队为此花了大量时间专门修稳定性，如今「我已经想不起上一次崩溃是什么时候了」。`mschuetz` 提供了一个正面体验：OpenShot 肯定不如 Premiere Pro 功能全，但运行顺滑稳健，而 Premiere Pro 老是崩溃，做简单任务也很繁琐。`t-writescode` 的看法是：只要有足够的时间、热爱和领导方向，任何以艺术为核心的开源软件都可能成为下一个 Blender 或 Krita。

`Almondsetat` 提了个真正的专业问题：公告细节太少，有没有实现常规的 hue vs hue、hue vs sat 之类的曲线控制？他的工作需要多机位，配合色卡和矢量示波器就能用这个替代 Resolve。`Maken` 贴了文档链接。`countrymile` 问 Blender 现在差多远，`embedding-shape` 回答：Blender 在「录制、剪辑、调色」三项里主要擅长剪辑，完全没有录制，调色只能走后期处理节点、还行但远不及 Resolve；如果你已经熟悉 Blender 快捷键，剪视频会非常流畅，但不值得为了剪视频专门学它。

**「AI 能驱动它吗」引发的关于软件未来形态的辩论**

`Schlagbohrer` 问有没有人试过让本地 agent（比如 Qwen）操作它，API 对程序化/CLI 使用友好吗。`drob518` 说这也是他的第一反应：「我们现在处于『万物皆 AI』的时代，所以每个应用似乎都需要某种 API 或 CLI，一切都需要机器可访问。」

`nasso_dev` 的反问引出了本帖最有意思的一段：「难道我们不该先关注**人类**可访问性吗？那本身也会顺带让东西更机器可访问，但至少人还是主角。再说 OpenShot 是 FOSS，你不能直接把源码丢给你的铁疙瘩让它自己改？」

`dmix` 把这个问题正式化：对设计师来说这是个大问题——未来的软件有多少是面向人的 UI，有多少是人对着聊天框打字（或者作为过渡形态，让 agent 去操作现有 GUI）。他认为目前 agent 驱动的软件还很小众、属于高技术用户，但随着主流化会改变，早期采用者会要求早期采用者的功能。`nasso_dev` 强烈反驳：**聊天窗口对很多任务来说是糟糕透顶的**，他真心希望这不是软件的未来——聊天界面绝无可能替代非线性视频编辑的 GUI。`phatskat` 补了个具体场景：「我不想『告诉』应用把几个片段的音频电平拉平，然后它把所有东西都归零，我还要花五分钟撤销。」`dmix` 的辩护是：每次他这么说，大家总是用当下的 UX 来理解；在他看来我们正处于 LLM 的 DOS/UNIX 时代——盯着一个空文本框、很慢、经常崩、GUI 集成基本不存在或很原始。他也承认这不可能完全替代视觉界面。`ReptileMan` 给出了折中：人类 UI 当然优先，但 UI 存在的意义是让软件做有意义的工作，所以每个设计良好的 UI 软件表面之下都会有一个随时可暴露的 API。`_joel` 的怀疑更直接：「我猜这是为了 agent 驱动，产更多 AI 视频垃圾。」

**「大多数人只想无损剪切拼接」**

`hn_submit` 提出了一个受到广泛响应的观点：他过去在财务上支持过 OpenShot，但现在倾向 LosslessCut 和 Shotcut，因为大多数人要的只是无损切割和拼接视频文件，不做任何转码，他认为**无损应该是所有这类编辑器的默认行为**。

`nickjay`（nickjs）分享了他用 mpv 加一小段 Lua 脚本扩展来可视化裁剪视频的做法，底层调用 ffmpeg，几秒完成且不重新渲染；多年前他用 shell 脚本做过同样的事，但 mpv 的可视化让它快得多。`bolangi` 分享了自己的 Perl 工具 App-fftrim。

`wvbdmp` 指出无损编辑要做很多牺牲：只能用兼容的输入流，只能在特定间隔上切割，这取决于编码器设置；他建议 NLE 可以默认以「锁定模式」导入片段，只支持无损操作，其余功能需显式启用。`j1elo` 提出了关键的优化思路：不受影响的部分（基本是全部）直接透传，只重新编码因为切点不在关键帧上而必须重编的那一小段——他说目前只知道 LosslessCut 的「Smart」模式做了这件事，希望更多大厂跟进。`Youden` 追问能否干脆保留整个 GOP，通过移动 PTS 或把多帧打包进单帧载荷让早期内容在播放时「消失」。`j1elo` 的回答是这个想法被讨论过但强烈不建议：**切割必须意味着底层字节确实不在最终结果里**，否则会造成数据泄露——想象你「智能剪掉」了视频里一段极其敏感的内容（比如个人信息），事后才发现素材其实还在，只需移一下时间戳就能重现。

**其他值得一提的**

- `zersiax` 是屏幕阅读器用户：目前在无障碍方面唯一算能用的视频编辑器是 Clipchamp，急需竞争者。他说自己期望不高，「但我想 x.0 版本或许正是我该开始自己修的时候，如果没人打算修的话」。
- `jonathanstrange` 说如果支持 VST 他就能用它替代 DaVinci Resolve。这引出了 `Joel_Mckay` 与 `efilife` 关于 YouTube 音频压缩的一场漫长且火药味十足的争论——前者称 Resolve 有「烘焙好的工作流」让音频在 YouTube 编码后保持完好，后者坚持 YouTube 用 LUFS 归一化、不会额外压缩，视频里演示的手动流程既不自动也没什么特别。`Joel_Mckay` 最后丢下一个「装傻钓鱼（sealioning）」的维基链接退出。最终由 `jonathanstrange` 给出了准确答案：Resolve 的导出设置里确实可以选目标真峰值或 LUFS 电平并自动归一化/优化，可以直接选「YouTube」预设，还内置对白电平调节器；`efilife` 接受了这个信息。
- 多人抱怨这类发布公告的形式问题。`localtoast2` 说这正是该配视频的场合；`ankit84` 说视频编辑器的落地页只放静态截图对新用户完全不公平，其威力只能靠 10 到 30 秒的内嵌视频展示。
- `conradfr` 报告 4.0 在他的 M1 Sequoia 上崩溃，并指出安装包名为 `OpenShot-v4.0.0-x86_64.dmg`「大概不是个好兆头」。
- `renegat0x0` 的两个问题代表了老用户的心结：编码快吗？编码时经常崩吗？「那是我几年前的体验，我决定跳过十年再来看它是不是都能用了。」
- `zikani_03` 注意到 AI 抠像用的是 ONNX 模型，并贴出了 openshot-onnx 仓库。
- `timonoko` 的调侃：「我梦想有一天这些能超越 1996 年写的 Cinelerra。三十年前啊。」`prmoustache` 纠正说 Cinelerra 的当前版本可不是三十年前的，那是三十年的开发积累。
