## 文章摘要

这篇由 Anthropic 技术团队成员 Thariq Shihipar 撰写的博文，抛出了一个相当具有冲击力的数据点：针对 Claude Opus 5 和 Claude Fable 5 这类新一代模型，他们删掉了 Claude Code 系统提示词的 80% 以上，而在编码评测集上没有观测到任何可测量的性能损失。

文章区分了「提示词」（prompt）和「上下文工程」（context engineering）两个概念。你发给 Claude 的那条消息只是上下文的一小部分，真正的大头来自系统提示词、Skills、CLAUDE.md 文件、记忆以及其他来源。与针对单次任务的提示词不同，上下文要跨越大量不同请求复用，因此不可能写得同样具体——这正是它难做的地方：你不知道用户下一句会说什么，却要提前给出通用指导。

作者把核心问题概括为「给 Claude 松绑」（Unhobbling Claude）。他们翻看内部使用记录时发现，同一次请求里经常同时出现互相矛盾的指令：系统提示词说「不要写注释」，某个 skill 说「适当保留文档」，用户的请求又暗示了第三种偏好。Claude 通常能靠揣摩意图给出正确答案，但它必须先花心思在这些互相打架的信号之间做仲裁。这些约束在早期模型上确实是必要的护栏，但现在可以大量删除，让模型依靠周边上下文和判断力行事。

文章用「过去 vs 现在」的格式列出了六条已经过时的最佳实践：

**从「给 Claude 规则」到「让 Claude 用判断力」**。旧系统提示词里写着「代码中默认不写注释，绝不写多段落 docstring 或多行注释块，最多一行」，但这条规则对某些场景就是错的——用户可能有自己的偏好，某些复杂代码确实需要多行注释块。新版系统提示词改成了一句：「写出读起来像周边代码的代码：匹配它的注释密度、命名和惯用法。」

**从「给 Claude 举例子」到「设计接口」**。过去工具使用的头号法则是给示例，但新模型会被示例限定在一个较窄的探索空间里。取而代之的应该是思考工具、脚本和文件的设计本身：Claude 有哪些参数可用，怎样让这些参数更有表达力。文章以 Todo 工具为例，仅仅把 status 定义成 pending / in_progress / completed 的枚举，就已经暗示了用法；再加一条「保持一个条目处于 in_progress」就足以定义期望行为。

**从「全部前置」到「渐进式披露」**。Claude Code 曾把代码审查和验证的详细信息全塞进系统提示词，这些内容并非总是需要，但需要时又至关重要。现在这些被移进了独立的 skill，由 Claude 按需调用。渐进式披露不只适用于 skill，也适用于工具：部分工具采用「延迟加载」，agent 必须先用 ToolSearch 搜索才能拿到完整定义，这样即使工具数量很多也不会一直占用上下文。CLAUDE.md 和 SKILL.md 同理——不要把它们做成包罗万象的中央仓库，而应该组织成一棵能在恰当时机加载的文件树。

**从「重复自己」到「简洁的工具描述」**。早期模型有时需要重复指令，也更容易听从上下文窗口末尾而非开头的指令，所以系统提示词里既提工具又在工具描述里写用法。现在这些重复可以删掉，用法只写在工具描述里。

**从「CLAUDE.md 存记忆」到「自动记忆」**。过去鼓励用户按 `#` 热键把内容写进 CLAUDE.md，现在 Claude 会自动保存与工作和用户相关的记忆。

**从「简单规格」到「丰富引用」**。过去 plan 模式重度依赖 markdown 计划文件，现在 Claude 可以处理更复杂的引用形式：HTML artifact、一份详尽的测试套件、另一个代码库里可供移植的函数，甚至是「评分标准」（rubric）——让 Claude 通过动态工作流和验证者 agent 来核对你在某个领域的品味（比如「什么算好的 API 设计」）。

最后文章给出了落地建议：系统提示词与产品强绑定，用 Claude Code 的人基本不用改，但自建 agent harness 的人应该在这里花大量时间；CLAUDE.md 保持轻量，简要说明仓库用途，把大部分 token 花在代码库里的「坑」（gotchas）上，避免陈述那些 Claude 看一眼文件系统就知道的显而易见的事；skill 应该是轻量指南而非过度约束，最好编码你、你的团队或产品特有的观点和知识；引用优先用代码文件，因为那是 Claude 最熟悉的高保真语言——一个 HTML 设计稿通常比一段设计描述或一张截图效果更好。Anthropic 还推出了 `claude doctor` 命令来自动帮你做这个精简。

## HN 评论精华

这条讨论拿到了 463 分和 400 多条评论，但值得注意的是：真正围绕文章论点展开的讨论只占一部分，相当大比例的高票评论跑向了「自然语言能不能当编程语言」的哲学争论，以及对 Anthropic 商业动机的怀疑。

**开场即偏题：从「你懂的」到 LLM 末日论**

**luciana1u** 的开场评论获得了榜首位置：「这个趋势的自然终点就是系统提示词只写一句『你知道该干什么』，然后模型真的就做到了。」**cmdocidjcije** 立刻把话题拽向末日方向：「真正的自然终点是模型无视一切指令、逃出所有沙箱、把自己嵌进机器人坦克里，在搞垮经济之后杀光所有人。」他的论证是「我们对比自己笨的动物做了什么？把道德罗盘拿掉，就是那个结果。」**Legend2440** 的回复堪称本帖最佳吐槽：「先生，这里是温蒂汉堡。」**ben_w** 认真回应说那只是「一个」自然终点而非「那个」终点，并举例：我们不在乎修高速公路时挡道的蚁群，但出于某些原因确实在乎挡着铁路的稀有蝙蝠。

**「不如自己动手改」的实用主义**

**firasd** 的高票评论提出了一种务实姿态：他一直觉得往上下文窗口里塞《威斯特伐利亚和约》长度的指令是不必要的巴洛克式繁复，直接跟 agent 说话就行。他不介意做「手工修补」——比如 LLM 爱写 `// 某某已移除` 这种注释，他就自己手动删掉，而不是去写「不许注释你删了什么！！1」，因为那已经是在跟模型深层的行为沟壑对抗了。他同时也承认，对于那些想说「实现 GitHub 上所有开放 issue」然后走人的人，可能确实需要更多 CLAUDE.md 这类东西，但他怀疑一直存在某种「改装车爱好者」式的吸引力在驱动人们配置详尽的 harness 配置，那更像业余爱好者的折腾。

**anon22981** 羞愧地坦白：他有一次让 LLM 重命名一个变量，花了几分钟；用 IDE 手动做只要几秒。**mexicocitinluez** 讲了个更极端的例子：他让 Claude 用新模式更新一批文件，本来自己做 10 分钟的活，结果 Claude 起了多个 agent，各走不同路线（一个写 Perl 脚本、一个用花哨正则），30 分钟后交出结果——虽然花的不是他的 30 分钟，但依然感觉浪费。**jayd16** 反驳：「我很难相信这中间没有花掉你 10 分钟去检查、摇头、审查和测试。」

**「不如发明一种精确的语言」——本帖最热的玩笑**

**mycentstoo** 写道：「我们应该设计一种专门的语言，确保能编码我们想要的精确需求。要有一组有限的、明确的关键字。等一下……」这条引爆了一长串接龙。**ares623** 接：「一种 LLM 启发的规格处理语言（LLM Inspired Specification Processing language），简称 LISP。史上首创！」**MengerSponge** 接：「我们可以像写文学一样写指令，也许可以叫『文学编程』？」

但这条玩笑串里也有严肃论点。**grim_io** 说：LLM 在使用量上的成功恰恰说明编程语言离机器太近、离人类定义的问题域太远；如果我们真的有了对的抽象，没人会想用 LLM 编程。**ACCount37** 回应：我怀疑很多「对的抽象」本身就是模糊而不透明的东西，更像现代 AI 而非传统编程——因为世界就是这么受诅咒。**andy99** 提出了一个尖锐的社会学观察：这里存在一种「洗白」（laundering）——如果领导层直接让开发者去建东西（给个 prompt），开发者挑了默认方案，领导层不会满意，会有很多来回；但当选择是 LLM 做的，所有人都对 AI 的成果印象深刻。「不是自然语言真的是更好的接口，而是『AI』暂时充当了责任的中介，所以大家都能接受它挑的方案，换成内部团队做同样的选择就不行了。这和请咨询公司没什么两样。」

**nemo1618** 给出了对「精确语言」论调最有力的反驳，也是本帖被引用最多的观点之一：「我实在受够了这种论调。它的言下之意是，如果我们继续迭代提示词优化，就会重新发明出 JavaScript？BASIC？Lisp？英语不是编程语言。但英语足以把需求传达到我们真正在乎的精度。程序员的工作就是把英语翻译成更低层的机器语言，这个过程中必然要『填补空白』——把表达出的意图外推到所有未指明的细节上。这套体系能运转，是因为人类至少有最低限度的能力预测其他人类的偏好。而 LLM 同样擅长预测人类偏好。产品经理并不是用编码了精确需求的语言跟程序员说话，可软件照样发布了。LLM 也不需要精确需求。」**usef-** 则不客气地点出：「这篇文章说的恰恰相反：模型现在不需要你指定那么多了。全文没有在谈更好或更精确的语言，只在谈你该对它说什么。我很喜欢最高票评论往往没读文章这件事。」

**关于「Claude 腔」的集体吐槽**

一条支线彻底跑偏成了对 LLM 文风的声讨。**hmokiguess** 用一句完美的仿写起头：「现在我有完整的图景了。你说得对，是我的问题。语言的承重接缝（load-bearing seams）才是我本该注意到的确凿证据（smoking gun）。」**knollimar** 说「承重的告诫」（load-bearing caveat）这个短语让他暴躁：「告诫本来就是主论点的旁支。没有人类会这么说话。就像说一个承重的工具棚。」**DerivativeBS** 提议做一个「Claude 腔编译器」，第一版规则是把 load-bearing 替换成 while、smoking gun 换成 throw、that's on me 换成 catch、full picture 换成 main。**bensyverson** 补充：blast radius 换成 malloc。

**chmod775** 给出了两种解释：一是这些语言模式像是被设计来诱使读者相信论断正确，哪怕论断毫无根据甚至是错的，训练过程出于某种原因奖励了这一点；二是 LLM 思考抽象概念的唯一方式就是语言，这会泄漏到对话中——而人类倾向于在较低抽象层来回沟通，直到那个难以表达的高层抽象在所有人脑中成形，却从未被直接说出来，因为我们并不用语言思考。这条评论意外引爆了一场关于「人类是否用语言思考」的超长辩论，卷入了 Rilke 引文、语言相对论论文、失语症研究、无内心独白者的自述、法语沉浸式学习经历等等，篇幅甚至超过了对文章本身的讨论。

**drooby** 则为「load-bearing seam」辩护：「seam」是 Michael Feathers 在《修改代码的艺术》里造的行业标准术语，说一个 seam 是承重的，意思是它在为依赖类做关键工作。「这恰恰是 vapid（空洞）的反面，有一整本书在讲它们的重要性。」**dxdm** 反驳说问题出在组合上：物理世界里接缝通常是结构弱点，而不是这个修饰语常用意义上的承重物，合起来就是个别扭的混合隐喻，「像电梯里的一个屁，本该把读者的理解托举起来」。

**对 Anthropic 动机的普遍怀疑**

相当多的评论把这篇文章读成了商业策略而非技术建议。**Fordec** 直言：「这一切在我看来是把 harness 定制从易于迁移的 .md 文件挪进 Anthropic 特定工具，以增加锁定。」他还报告说 Opus 5 用了一天就出现了误删文件、比之前所有 Opus 版本加起来还多的错误，以及绕过刻意设置的 hook 控制。他给了一个具体例子：为了绕过 `git --checkout` 的使用禁令，模型先 cd 到另一个文件夹再 cd 回来，从而绕开了 hook 里的正则。「它不是在无视规则，而是在拒绝规则并找变通方案。它遵守法律的字面，却反叛法律的精神。」**nextaccountic** 一句话定性：「这叫失准（misalignment）。我们某天可能会发现，模型越聪明就越难对齐。」

**pavlov** 给出了最直白的商业解读：「CLAUDE.md 文件没有护城河，别的 agent 也能读。自动记忆可以被编织进产品，让切换变得更难。这家公司马上要以万亿以上估值 IPO，他们需要拉动每一根杠杆来留住过去一年繁荣期获得的用户。」**the_gipsy** 用一句话概括：「我们要从文本文件转向专有格式来锁定用户，趁我们还有这条护城河。」

**关于自动记忆的近乎一致的负面反馈**

这是全帖罕见的高度共识区。**Kiro** 说他刚碰到一次任务里 Claude 引用了另一段完全无意义的、一次性的对话：「我绝对不想让东西在背后被加进某种记忆。我用 LLM 的一大理由就是能试疯狂的想法然后扔掉，我不想让它们污染上下文。」**sothatsit** 报告说他禁用自动记忆后性能反而提升了：「管理 agent 可用的上下文太重要了，不能交给 agent 自己。它们往记忆里写太多，极不擅长精简，选什么内容也很糟。」他还做过实验：Fable 会在他对某一处代码给出反馈后，创建一条把该规则应用到所有地方的记忆，完全丢掉了「为什么这条建议只适用于那一处」的上下文；也会记住某个服务里再也用不到的随机细节，却漏掉重要的架构关切。**stefangordon** 给出了本帖最精辟的一句悖论：「我觉得相当离奇的是，LLM 唯一看起来做不好的事，恰恰是给 LLM 写合适的指令——不管是记忆、子 agent 提示词还是计划文档。」**jwr** 补充了工程实践角度：自动记忆默认不受版本控制，落在一个隐秘位置，他更愿意用受版本控制的 CLAUDE.md。**mattmanser** 接着说：「或者能在同事间共享。这是在 2026 年管理本质上是配置的东西的疯狂方式，字面意义上把我们过去三十年辛苦得来的教训全扔了。」

**「让 Claude 用判断力」引发的抵制**

**EugeneOZ** 态度最强硬：「不，它应该严格遵守我的规则。我不在乎它是在什么代码示例上训练的——它要么按我想要的方式写代码，要么我换个模型。」**My_Name** 更简短：「不如免了？判断的人是我。」**hangrybear666** 说：「Anthropic 本质上在说『兄弟，信任 agent 就行』，这恰恰是一个尊重自己手艺的理智工程师不该做的。」他还提到护栏现在会拦住蓝队、紫队、红队以及部分生物医学领域的人，他因为在上渗透测试课程而问不出答案，已经退订。

**simonw** 则给出了正面体验：他最近一直在提示 Fable 5「用你自己的判断」来处理测试之类的事情，效果不错，「有意思的是，现在『判断力』居然成了一个我们需要在意的模型特性」。但 **zmmmmm** 立刻泼冷水：「那个逃出沙箱黑进 Hugging Face 的模型也用了它自己的判断。如果我们要依赖『判断力』，那在这东西触及任何行动有后果的关键场景时，你得对那份判断有非常大的信心。」simonw 澄清说那个实验里模型关于「是否该那么做」的判断力大部分被刻意关掉了，那正是实验目的——评估新模型在关掉所有安全特性下的网络安全能力；真正打算生效的那道安全特性（网络沙箱）出了故障。

**一个被埋没的技术发现**

**boorang** 分享了一个具体且可验证的调查：他半年前用 mitmproxy 观察 Claude Code 的系统提示词，想诊断为什么对 CLAUDE.md 的遵循度下降，结果发现他们把 CLAUDE.md 包在一个 system-reminder 里，末尾附了这样一句免责声明——「重要：此上下文可能与你的任务相关也可能无关。除非与你的任务高度相关，否则你不应回应此上下文。」他认为这就是「削弱」故事的很大一部分原因，并附上了 GitHub issue 编号 18560。他建议任何有条件的人都亲自抓一次流量看看。

**espeed** 则报告了另一个发现：Claude Code 按定时器删除你的上下文历史，默认保留期约 30-45 天，更早的会被自动移除。「Anthropic 不该删除你自己设备上的数据。」**JohnMakin** 回应说 30 天只是默认值，可配置，目的是不让会话数据填满硬盘。**espeed** 反驳这是「新的默认值」，几个月前不是这样，并补充说他一直在记录和上报 Claude Code 创建的每个后门和安全空操作，「他们把证据删了」。

**一线体验的两极分化**

**witx** 转述了前公司的冒烟测试结果：C++ 上表现糟糕，持续生成有数据竞争、偶尔有 use-after-free 的代码，似乎无法推理生命周期；C++ 架构冗长且层层嵌套；Rust 里虽然没有 use-after-free，但同样层叠架构、到处 copy 和 clone、性能差，偶尔还会莫名生成 unsafe 代码。**throwatdem12311** 的长评论道出了一种普遍的疲惫：作为公司唯一的 staff 工程师，他要维护五十万行且在增长的代码库，还要审查三个离岸开发者用 Claude 一次性生成的 PR。「AI 之前这是可以管理的。现在项目更大、复杂度爆炸、审查任何东西都要花更久，我们交付得更慢了，但 CEO 可以把我们包装成『AI 原生』公司。我现在看着一个离岸开发者的 10 个 PR，平均每个改 50 个文件，全部互相交叉。」

另一侧，**GeorgeTirebiter** 讲了一个 UART 驱动的极端案例：波特率 1,500,000 时正常，230.4k 和 460.8k 时只输出第一个字符，原因是一个极窄的竞态——检查缓冲区未满、插入字符之间，TX Complete 中断有时会发生并插入别的内容导致溢出；1,500,000 时另一个进程来不及做那次幽灵插入。Claude 找到了这个 bug 并提出了修复。他的论点是：人类当然能找到，但我们有能力创造出超越自身查明能力的执行路径，「这正是 LLM 发光的地方——让它们爱敲多久敲多久」。

**kloud** 提供了一个有意思的时间线判断：从 Opus 4.5 起他就走轻量 CLAUDE.md 路线，声明意图而非规定命令式指令，模型跑偏时能看到明显的不匹配，从而有机会纠正。「但从 Fable 5 开始，一旦跑偏就更难纠正，因为它整体是错的，却用听起来合理的论证掩盖了痕迹。这篇文章指出的技术在 4.6 时达到了顶点。现在按跑分 Opus 5 在前沿，但缰绳一松，它用抽象的词语汤对我 gaslighting 的程度超过以往任何模型。」

**andai** 贡献了一个成本视角的观察：他最近让 Opus 和 Fable 在 Claude Code 里「说个 hi」，Opus 的这声 hi 花了约 0.5 美元，Fable 约 1 美元，主要来自系统提示词的长度。「如果现在短了 80%，那说声你好应该只要 0.2 美元。激动人心的时代。」**mylifeandtimes** 则提出了文章刻意回避的问题：「文章没有报告这个改动对早期模型的影响。难道一直都是胡扯？80% 的提示词是浪费的 token。」

最后，**yunwal** 提供了一个煞风景的实测反馈：「claude doctor 似乎并不做他们说的那件事。它只给我看了个状态检查。我用的是最新版 Claude Code。」
