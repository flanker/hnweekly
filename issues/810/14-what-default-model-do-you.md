## 文章摘要

发帖人 stikit 的问题很直接：你日常默认用哪个模型？他自陈的情况是——大部分工作用 Claude，但顶配的 Fable 对他来说明显过剩，开四个 agent 做一次移动端项目的初步规划就能在几分钟内烧光 Max 套餐的会话额度；等了六小时冷却期回来接着干，缓存又已经过期，一分钟内又烧掉 2%。于是他退回 Opus 4.8，觉得「够用」、性价比好，在看到明确理由之前不打算升回 5。帖子拿到 63 分、107 条评论，规模不大，但信息密度很高，基本可以当作 2026 年 9 月开发者用模型的一份非正式普查。

**最突出的结论是：「一个默认模型」这个前提本身已经过时了。** 绝大多数回答给的不是一个模型名，而是一套分工方案。典型配置是：便宜快速的小模型当日常主力跑实现，贵的强模型只在规划、找难 bug、做最终 review 时进场。有人在 shell 里做了个 `ask` 别名直接调 Haiku 处理网页搜索、简单命令和日志分析；长任务则先让 Fable 写一份 PLAN.md，并明确告诉它「这份计划会由别的模型执行」，结果它自己就会指派 Opus 或 Sonnet。他说自己以前是「所有事都上最强模型」，按任务拆分之后速度和结果都更好。

**第二个明显趋势是价格敏感度急剧上升，开源权重模型和中国实验室的模型占比很高。** GLM-5.3-flash 在本帖出现频率极高，多位用户把它设为全部 agent 的默认执行模型，评价是「非常能干、很便宜，就是啰嗦、不算最快」。DeepSeek v4.1 flash 是另一个高频答案。还有人用 Qwen 3.8 系列、Gemma、Muse Spark、K3、Composer 等。反过来，**amelius** 在中段插了一句「读下来感觉用中国实验室模型的人不多」，结果下面立刻涌出一批 DeepSeek / GLM 用户——这条自身就成了一个有趣的观测偏差样本。

**第三个反复出现的主题是 Claude 的「文风」问题**，而且是与能力分开来谈的。多位用户明确表示 Opus 4.6–4.8 的英文还算正常，Opus 5 变得「难以忍受」——不是答案错，而是话太多、太绕，读它的输出比自己写还累。有人说这直接导致他产生心理抗拒，不愿意再打开 Claude Code。也有人从反方向描述同一件事：从 Gemini 换到 Claude 后，写代码很满意，但一让它解释某个模块，就会得到好几页本可以两段说清的内容，结果是「看着就开始拖延」。

**第四个主题是消耗量的巨大差异。** 同一份 20x 套餐，有人一天就跑光，有人「就算刻意想用光也用不完」。追问之下，那位一天见底的用户给出的答案是：7×24 跑多 agent 自主 devops，外加训练一个果蝇大脑来驱动自动驾驶系统，每周合入 300 多个 PR。另一位每天用 Astra 低档也能撑过一周的用户则指出关键在于是否使用 orchestrator 这类吞 token 的模式。**rsyring** 干脆提议：这种问题要可比，至少得先说明预算、开发类型（是给家人做 HTML 联系表单还是实时航天推力矢量控制）、以及人机协作方式（短回合人在环 / 能跑好几天的软件工厂 / 居中）。

一个反复出现的次级观点是：**「harness 工程」正在比模型选择更重要。** 有人表示自己在 Opus 4.7 前后达到能力峰值，之后试图把自己从回路里摘出来、靠可验证的测试和快速反馈让前沿模型自主运行，但扩展性不好——模型「特别擅长让我觉得它通过了测试，然后过一阵才暴露出逼我大改的技术债」。还有多人强调自己刻意保持 harness 和订阅解耦，把 issue 存在独立工具里，随时能换模型换 harness，「忠于某个模型或 harness 看起来不明智」。

## HN 评论精华

- **beej71** 贡献了本帖最精炼的元评论：「看看这里答案的花样之多，不禁让人怀疑这事到底有多要紧。让我想起问一群摩托车手该用什么机油。」

- **montroser** 发起了本帖最激烈的一段争论。他的立场是：对 99% 以上的 Web 和移动端任务，deepseek-v4.1-flash 完全够用——飞快、极便宜、相当靠谱，视觉能力足以自己检查 UI 产出，而且「比任何 Anthropic 模型都少几分自得和辞藻」。他说自己整天开着好几个会话，零售价一天约 2 美元，配 opencode-go 的话实际就落在 10 美元/月的订阅里。被追问「你到底在痛什么」时他说得更直白：按单任务成本算，Fable 是 DS4.1 的 32 倍，「要么真的多烧那么多电和 GPU，要么就是让大众相信日常任务非它不可——两种都是悲剧」；他更在意的是，如果写代码必须付出堪比很多人月租的钱，那休闲编程这件事本身就被定价挤出去了。

- 这段引来了 **AaronAPU** 的硬回击：「我每月付 200 美元，从来没有一次跑满额度，它比 DeepSeek 好，而且至少支持的是一家美国公司。你的痛苦对我不重要。」montroser 回敬「何不食肉糜」，并把选择框定成一边是与军方合作、按政府要求自我审查、为建数据中心大肆消耗资源的美国公司，一边是开放权重、投入效率优化的中国公司。AaronAPU 的收尾是「我们大多数人看到这种话就翻个白眼继续过日子」。这段交锋很好地展示了 2026 年模型选择已经不只是技术问题。

- **bellowsgulch** 的回答被顶得很高，但真正的重点在后半段离题的部分。他日常用 mimo-v2.5-free、mimo-v2.5、deepseek-flash，观点是「大多数工程任务不需要前沿模型，卡住了再往上升」，买 Claude 套餐在他看来毫无必要。随后他话锋一转：模型擅长的那些事是双刃剑——除非你有 LLM 之前积累的、确实写得好设计得好的作品集，否则你的产出看起来就是「假装设计精良的 slop」，排版糟糕、布局糟糕，哪怕用了流行的 CSS 框架也一样。他的结论是「烂工程师永远是烂工程师，工具补不上」。

- **hgoel** 代表了本帖里的本地化路线：个人用途跑在 GB10 集群上的 Qwen3.8-Next-Flash，工作则用 Copilot 配 GPT-5 mini 或按复杂度在 Opus/Sol 之间选。他原本付 Claude 20x 全量用 Opus，转向本地的理由列了三条：讨厌现在的说话方式；以及一系列行业事件。他补充说两台 Spark 峰值共约 150W，电费大概一个月一美元，但硬件本身各 4000 美元，总投入约等于好几年的顶配订阅——换来的是可以放心把内网凭证交给模型去修 proxmox 服务器的 nvme 问题。

- **conradludgate** 给出了一个少见但具体的选型理由：他工作中大量时间花在给自己的服务做安全加固，而「Sol 和 Opus 老是打小报告、拦我的 prompt」，所以更偏好开源权重模型。

- **time0ut** 是本帖里少数明确推荐 Cursor 的人，理由集中在 Composer 一个点上：便宜、快、下刀准的「主力马」。他的判断是「Claude Code 还行，但缺一个好用又快又便宜的 workhorse，Sonnet 和 Haiku 都不是」。

- **philbo** 给出了一条与主流「让 agent 自主跑」相反的理由：「我喜欢快模型，因为我全程都在参与。我不把控制权整个交给 agent，那样最后的结果反而更难理解。」
